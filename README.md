# RustFS · 飞牛 fnOS 应用包

把 RustFS 做成飞牛 NAS 应用中心里的一个应用：点几下装好，桌面上多一个图标，点开就是 Web 控制台 —— 不用手写 `docker-compose.yml`，也不用登录 SSH。

本包封装自 RustFS 官方镜像，上游项目见 https://github.com/rustfs/rustfs 。

## 想把数据放到自己的存储空间？两步

> **要改数据目录，请按两步走（顺序不能反）：**
> 1. **先到「应用设置 → 访问权限」把这个目录添加/授权**给本应用；
> 2. **再回到「运行设置 → 数据存放位置」**选「改到下面填写的目录」，填**同一个路径**并保存。
>
> 为什么必须先授权：fnOS 是按「应用用户」单独授权的（TrimACL），没授权时本应用写不进去，第 2 步就会报「数据目录不可写」。

安装时不需要选目录（默认用应用自己的数据目录），改目录只在「应用设置」里做。

## 这是什么

一个 fnOS 应用包（`.fpk`）。在飞牛 NAS 的应用中心里点「手动安装」，选中下载好的包，等它装完，桌面上就会多一个入口。打开就是 RustFS 的 Web 控制台。

容器由应用中心托管：装好后可以在应用中心里启动、停止、看状态，跟其它应用一样，**不需要你手写 `docker-compose.yml`，也不需要登录 SSH**。

## 它能干什么

RustFS 是一个兼容 Amazon S3 协议的对象存储。放在自己的 NAS 上，常见用法是：

| 场景 | 说明 |
|---|---|
| **备份目标** | 很多备份软件支持「S3 兼容存储」。把备份写到自家 NAS，不经过公有云，数据不出门。 |
| **媒体库 / 图床后端** | 一些媒体服务器、相册、图床类应用可以把对象存储当后端，文件集中存放、统一由应用管理。 |
| **给其它应用提供对象存储** | 自托管应用常需要存附件、导出包、日志归档。有个本地 S3 端点，就不必每个应用各存一份目录。 |
| **只是想在 NAS 上试试 RustFS** | 不想为了看一眼去敲一堆 docker 命令，那就用它。 |

> 需要提醒一句：**对象存储不是备份方案本身**。它只是一个能存东西的地方；如果里面的东西对你有价值，仍然要另外做备份（快照、复制到另一台机器等）。详见「已知限制」。

## 安装三步

1. **下载**：到本仓库 **Releases** 页面，下载对应架构的包（当前只有 x86）：
   `rustfs-fnos-1.0.4-x86.fpk`，以及同一页的 `SHA256SUMS`。
2. **安装**：登录飞牛 fnOS → 应用中心 → 左下角「手动安装」→ 选择刚下载的 `.fpk` → 按向导填写 → 完成。
3. **打开**：安装完成后，桌面上会出现「RustFS」图标，点开即控制台；也可以直接访问 `http://<你的NAS地址>:9201`。

详细步骤（含校验、向导每个字段是什么意思、建第一个桶、用 S3 客户端连上去）见 **[docs/install-fnos.md](docs/install-fnos.md)**。

## 升级

**走应用中心的界面升级，不要在命令行里折腾。** 具体原因见下表。

| 方式 | 能不能用 | 说明 |
|---|---|---|
| 应用中心 Web UI → 上传新包 / 升级入口 | ✅ **唯一正确路径** | 会执行应用的升级流程：记录当前镜像、备份配置、按新包重建容器 |
| `appcenter-cli install-fpk <新包>` | ⚠️ 对**已安装**的应用会直接返回「已安装」，不会升级 | 别指望它 |
| `appcenter-cli install-local` | ❌ **不要用** | 它的语义等于**卸载再安装**：凭据会被重新生成，所有已接入的 S3 客户端都要改配置 |
| 手工改 compose 再 `docker compose up` | ❌ 不推荐 | 绕过了应用的校验流程，状态会与实际不一致 |

升级时会发生什么，三件事提前知道：

1. **服务会中断一会儿。** 升级要重建容器，这期间 S3 API（9200）和控制台（9201）都不可用，通常几秒到几十秒（取决于镜像是否已在本地）。建议放在没人用的时候做。
2. **重建容器本身不动数据** —— 桶与对象在数据目录里，不在容器里。**但有一个例外必须先知道**：如果安装/升级在「应用初始化」阶段失败，平台的失败回滚可能把数据目录和配置目录一起删掉。这一条见下面的「升级前必做」，别跳过。
3. **回滚只还原镜像。** 如果新版本有问题需要退回，应用能做的是「把镜像引用改回上一个」，**不会**还原端口、环境变量、数据目录路径这些配置。详见 [docs/faq.md](docs/faq.md)。

升级后如果发现「版本号显示没变」或「状态变成失败」，先别急着重装 —— 大概率是镜像还没到位，看一眼 [docs/faq.md](docs/faq.md) 的两条问答，多数情况只要在应用中心「停止 → 启动」一次就自愈。

### ⚠️ 升级前必做：先备份数据（30 秒）

**风险是什么。** 安装或升级如果停在「应用初始化」阶段（脚本开始跑之后报错），fnOS 应用中心会执行一次**失败回滚**，把本应用的数据目录和配置目录整个删掉 —— 包括你已有的桶和对象。这不是本应用想删（我们的卸载脚本在「保留数据」分支里没有任何删除动作，已核对代码与日志），而是平台的失败处理行为，我们控制不了，只能提前备份。

- **已确认**：先卸载再安装、且安装阶段失败 → 数据与配置一起消失（真机复现，并有「失败发生在更早阶段、数据完好」的对照实验）。
- **尚无法确认**：在应用中心用新包做「升级」时若失败，是否同样回滚删数据。我们没有证据，所以**请按最坏情况准备**。

**保命操作（升级前 30 秒）：**

```bash
# 1) 先确认应用名。本包是 rustfs-fnos；如果你不确定，用下一条命令看
appcenter-cli list

# 2) 备份数据目录（同级放一个带日期的副本，不要放进 data/ 里面）
sudo cp -a /vol1/@appdata/rustfs-fnos/data \
           "/vol1/@appdata/rustfs-fnos/data.bak-$(date +%F)"

# 3) 确认备份真的有了（大小应该和原目录差不多）
sudo du -sh /vol1/@appdata/rustfs-fnos/data \
           /vol1/@appdata/rustfs-fnos/data.bak-*
```

仓库里也提供 `scripts/backup-data.sh`，用法 `sudo ./scripts/backup-data.sh <app名>`，行为等价（多一层时间戳与空间检查）；不确定时以手工命令为准（参数以仓库内 `--help` 输出为准）。

关于路径：`/vol1` 是**第一个存储空间**。如果你把它装在别的卷上，路径可能是 `/vol2/…`、`/vol3/…`。用下面这条命令确认实际位置，再照抄上面的命令：

```bash
ls -d /vol*/@appdata/*/data 2>/dev/null
```

**升级并验证成功之后，再删备份：**

```bash
sudo rm -rf "/vol1/@appdata/rustfs-fnos/data.bak-2026-10-27"   # 换成你实际的日期
```

**如果数据很重要，升级前请先停掉所有连它的客户端** —— 备份任务、媒体服务器、其它自托管应用。原因很实际：万一数据目录被回滚删掉，这些客户端会继续往里写，等你恢复备份时它们已经在「空库」上跑了一段时间，容易把状态搞乱。

**恢复备份的做法**（只在确认数据确实没了之后做）：

```bash
# 1) 确认应用已停止（应用中心里点「停止」，不要带病覆盖）
# 2) 把备份复制回原位
sudo cp -a "/vol1/@appdata/rustfs-fnos/data.bak-2026-10-27/." \
           /vol1/@appdata/rustfs-fnos/data/
# 3) 修正归属（容器以 UID/GID 10001 运行）
sudo chown -R 10001:10001 /vol1/@appdata/rustfs-fnos/data
# 4) 回应用中心「启动」
```

## 端口

| 端口 | 用途 | 说明 |
|---|---|---|
| **9200** | S3 API | 其它应用 / S3 客户端连这个端口。不是网页。 |
| **9201** | Web 控制台 | 浏览器打开这个看界面、建桶、管用户。 |

- 两个端口在安装向导里都能改。若提示端口被占用，改成其它空闲端口即可（例如 9300 / 9301）。
- **改端口只影响宿主机对外暴露的端口。** 容器内部监听的一直是它自己的固定端口（9000 / 9001），所以改完**不需要**动任何应用配置，也不需要重启 NAS。
- 端口只在局域网内提供访问。**不要直接把 9200/9201 映射到公网**——RustFS 有自己的账号体系，暴露到公网等于把存储服务挂到互联网上。

## 管理员账号与密码

**账号和密码由你在安装时自己填**，装完直接用它们登录控制台 —— 不需要再去任何文件里找。

- 安装向导里有两项：**管理员账号**、**管理员密码**。这就是 RustFS 控制台的登录账号，也是给其它应用、备份软件用的 S3 凭据（Access Key / Secret Key）。
- 自己定一个好记但不好猜的。**不要**用 `admin`、`root`，也不要用上游文档里那组公开的默认值（`rustfsadmin`）。
- 想换一组：应用中心 → 该应用 → **配置/设置**，在向导里重设即可，不用卸载重装，数据也不动。
- **忘了密码、进不去控制台**：先在「配置/设置」里重设；如果那里没有这一项，再 SSH 登录 NAS 从应用的配置目录读回当前凭据（路径与命令见 [docs/install-fnos.md](docs/install-fnos.md) 的「忘记密码」一节）。
- **一条要记住的边界**：卸载会清掉应用的配置目录，这组凭据跟着没了；重装时你要重新设一组，已接入的备份工具/媒体服务器都要改成新的。

## 离线安装限制（重要）

**本包不包含镜像。** 安装完成、应用启动时，需要把 `rustfs/rustfs` 官方镜像放到设备上。

这里有一处**容易误解的地方**，先说清楚：

> **应用自己不能拉镜像。** 它以一个专用低权限用户（包用户）运行，而 fnOS 的镜像加速站要求请求里带一组签名头，这组签名头只写在 **root 的** docker 配置里，包用户读不到。所以应用运行期去联网拉镜像**必然超时失败**——这是平台的设计，不是故障，也不是本应用的 bug。

镜像实际上是由**应用中心（以 root 运行）或你自己用 `sudo`** 拉下来的。所以当你看到「拉取失败 / 超时」时，正确的处理是：

1. 用 SSH 登录 NAS，以管理员身份执行 `sudo docker pull rustfs/rustfs:1.0.4`，看它是否成功；
2. 成功后回应用中心「停止 → 启动」一次，应用会自己发现镜像已就位并完成切换。

其它三条辅助办法：

- **配镜像加速**：在 fnOS 的 Docker 相关设置里配置可用的镜像加速地址（面板位置以你设备上的实际界面为准）。
- **离线导入**：在一台能联网的机器上 `docker save rustfs/rustfs:1.0.4 -o rustfs.tar`，传到 NAS 后 `docker load -i rustfs.tar`。
- **确认网络**：在有外网的机器上 `curl -I https://registry-1.docker.io/v2/`，正常返回 `401`；超时说明出口不通。

> 我们选择「安装时拉取」而不是「把镜像塞进包」，是为了让包保持很小、也让镜像更新更容易。代价就是上面这条网络依赖，这里如实说明，不含糊。

## 常见问题（摘要）

完整版见 **[docs/faq.md](docs/faq.md)**（含「用户可见行为总表」）。

**Q：镜像一直拉不下来／提示超时怎么办？**
A：应用自己拉不了（见上一节）。用 `sudo docker pull rustfs/rustfs:<tag>` 手动拉，成功后回应用中心「停止 → 启动」。若 `sudo docker pull` 也超时，是设备出口网络问题，先解决网络。

**Q：升级后版本号没变／状态显示失败怎么办？**
A：多数是镜像还没换到本地。应用会在升级后发现「配置里写的镜像」与「容器实际在跑的镜像」不一致，并在 15 分钟内持续等镜像到位；超时就把状态标成失败，同时给出「三步修复 + 回滚命令」的文字指引，写在应用的日志里。**你通常只需要：`sudo docker pull` 目标镜像 → 应用中心「停止 → 启动」**，应用会自己比对、重建容器并校验。别急着卸载重装——那会换掉凭据。

## 已知限制

| 限制 | 说明 |
|---|---|
| 仅 x86 | ARM 设备不支持。上游镜像是否提供其它架构，以镜像仓库页面为准。 |
| **安装/升级失败可能删除数据与配置** | 安装/升级若在「应用初始化」阶段失败，平台回滚会删除本应用的数据目录与配置目录（含桶与对象、含凭据）。**已确认**的是「先卸载再安装、且安装阶段失败」这条路径（真机复现，另有「失败在更早阶段、数据完好」的对照）；**应用中心升级失败是否同样回滚尚未确认，按最坏情况准备**。**把数据目录设到你自己的存储空间可规避此风险**（见 [docs/install-fnos.md](docs/install-fnos.md) 的「数据放哪里」）。预防与恢复做法见上面「⚠️ 升级前必做：先备份数据（30 秒）」。 |
| **升级期间服务中断** | 升级要重建容器，这期间 9200/9201 都不可用，通常几秒到几十秒。建议在维护窗口做。 |
| **回滚只还原镜像** | 应用能回退的是「容器用哪个镜像」；端口、环境变量、数据目录路径这些配置**不会**被还原。回滚后如果发现配置也不对，需要人工核对。 |
| **卸载会清除凭据** | 卸载会删掉应用的配置目录，包括 Access Key / Secret Key。重装时你要**重新填一组**，旧的那组立即 `403 InvalidAccessKeyId`，所有已接入的 S3 客户端都要改配置。 |
| **卸载会移除应用使用的镜像 tag** | 实测：卸载后本地的 `rustfs/rustfs:<版本>` 这个 tag 会消失（镜像本体若还被其它 tag 引用则仍在）。重装同一版本时可能因此触发拉取，而应用自己拉不动镜像（平台限制），表现为「装完起不来」或等约 15 分钟后判失败。处理：`sudo docker pull rustfs/rustfs:<版本>`，再回应用中心「停止 → 启动」。详见 [docs/install-fnos.md](docs/install-fnos.md) 的卸载一节。 |
| **同一版本不能重装，`install-local` 等于重装** | `appcenter-cli` 对已安装应用一律返回「已安装」；`install-local` 的语义是卸载再安装（会换凭据）。升级请走应用中心 Web UI。 |
| **应用自己不能拉镜像** | 平台设计：签名头只在 root 的 docker 配置里。镜像由应用中心或管理员用 `sudo` 拉取，应用只负责比对与校验。 |
| **镜像没换会被判失败，等 15 分钟** | 升级后若容器仍跑旧镜像，`status` 会在 15 分钟（墙钟）宽限期后返回失败并给出修复指引。拉好镜像后「停止→启动」即可自愈。 |
| **上游同 tag 重推（digest 变了）检测不到** | 我们只比对镜像引用字符串，无法得知某个 tag 在镜像仓库上的内容是否被替换。**发布纪律：每次发版必须换新 tag，不要复用旧 tag。** |
| 凭据由你自己设定 | 向导里填的管理员账号密码就是控制台与 S3 的凭据。卸载会清掉，重装要重新填，已接入的客户端都要改。 |
| 需要联网拉镜像 | 见上面「离线安装限制」。 |
| 单盘部署无法原地扩容 | 这是 RustFS 上游的限制：单机单盘（SNSD）不支持原地扩容，也不能作为 Pool 加入。想扩容只能新建一个实例，用 S3 工具把数据迁过去。选存储位置时请一次选够。 |
| 不做 TLS / 证书管理 | 本包只提供 HTTP 访问，供局域网使用。需要 HTTPS 请自己在前面加反向代理。 |
| 不接管 fnOS 的登录态 | RustFS 有自己的账号体系。本应用不会用你的 fnOS 账号登录控制台，也不与 NAS 用户打通。 |
| 不跟随上游 `latest` | 本包固定绑定一个具体的上游版本（当前 `1.0.4`）。上游发新版后需要我们更新这个包，不会自动升级。 |
| 上游行为变化不保证兼容 | 若上游改了数据格式或接口，我们在新版本包中说明迁移方式；旧版本的包会保留在 Releases 里。 |

- 装了有问题 → 提 [Issue](.github/ISSUE_TEMPLATE/bug_report.md)，请按模板填 fnOS 版本、架构、应用版本与日志。
- **RustFS 本身的功能问题、漏洞、性能问题** → 请报给上游：https://github.com/rustfs/rustfs/issues
- 安全问题 → 走 [SECURITY.md](SECURITY.md)，不要开公开 Issue。
- 这是个人维护的项目，**不承诺响应时间**。修复与否取决于问题严重程度与我的时间。

# 如何验证「你下载的包就是我发布的包」

本文解决的问题只有一个：**你手上这个 `.fpk`，是不是从本仓库 Release 出去的那一份，途中没被换过。**

为什么要做这件事：`.fpk` 里面包含安装时会执行的脚本。包被替换，等于有人能在你的 NAS 上以应用身份执行代码。校验只需要 30 秒。

---

## 一、核心概念：两条独立信道

| 信道 | 谁知道它 | 证明什么 |
|---|---|---|
| 安装包本体（`.fpk`） | 任何人可下载 | — |
| **发布方公布的 SHA256 值**（`SHA256SUMS` 文件 + Release 说明里写一份） | 从本仓库发布页取得 | 你手上的文件与发布时的文件**逐字节相同** |

只做「包能解开」不算校验——那只能说明文件没损坏，不能说明没被换。**必须比对哈希值。**

---

## 二、校验步骤（三步）

### 第 1 步：把两个文件放在同一个目录

从 Release 页面下载：

- `rustfs-fnos-1.0.4-x86.fpk`
- `SHA256SUMS`

放在同一个文件夹里。

### 第 2 步：按你的系统执行校验

**Linux**

```bash
cd 下载目录
sha256sum -c SHA256SUMS
```

**macOS**

```bash
cd 下载目录
shasum -a 256 -c SHA256SUMS
```

**Windows（PowerShell）**

```powershell
cd 下载目录
Get-FileHash .\rustfs-fnos-1.0.4-x86.fpk -Algorithm SHA256
```

然后打开 `SHA256SUMS`（记事本即可），把里面的值和上面输出的 `Hash` 逐字符对比。
（Windows 没有内置的 `sha256sum -c`，所以是「各自算、人工比」。想省事可以装 Git for Windows 后用 `sha256sum -c SHA256SUMS`。）

### 第 3 步：和 Release 说明再对一次

本仓库的每次 Release，正文里都会单独写一份 sha256。把第 2 步的结果和 Release 正文里的值比一次。

```
第2步算出来的值  ==  SHA256SUMS 里的值  ==  Release 正文里的值
```

三个值一致 → 通过。任一不一致 → 见下面「校验失败怎么处理」。

`SHA256SUMS` 的内容长这样（一行一个文件）：

```
<64位十六进制>  rustfs-fnos-1.0.4-x86.fpk
```

---

## 三、校验失败怎么处理

| 情况 | 处理 |
|---|---|
| 值与 `SHA256SUMS` 不一致 | **不要安装。** 删掉文件，重新下载一次再算 |
| 连续两次不一致 | 停止安装。这可能意味着下载源被劫持或 Release 资产被替换，请提 Issue 告知（附上你算出的值） |
| `SHA256SUMS` 里没有你要的文件 | 说明该资产漏传。回 Release 页面确认文件名，不要"自己算一个"绕过 |
| 文件大小与 Release 里显示的不一致 | 按传输不完整处理，重新下载 |
| 包能解开但哈希不对 | 依然**不通过**。能解包不代表没被换 |

---

## 四、包里面是什么（看懂结构，判断有没有异常）

解开 `.fpk` 看结构（只读，不会执行任何东西）：

```bash
tar -tzf rustfs-fnos-1.0.4-x86.fpk
```

正常情况下你会看到这些条目（`.fpk` 本质是一个 gzip 压缩的 tar 包）：

| 条目 | 是什么 | 值得注意的地方 |
|---|---|---|
| `manifest` | 应用元数据（应用名、版本、架构、入口名等），纯文本 | 里面有一行 `checksum=`，是打包工具自动生成的包内校验值。**它只证明包内自洽，不能证明来源**，所以不能替代上面第 2 步的 SHA256 |
| `cmd/` | 生命周期脚本（安装、启动、停止、状态、升级、卸载） | 想看这个包会做什么，就看这里。都是 shell 脚本，可以直接读 |
| `config/` | 权限与资源声明（以什么用户运行、需要什么资源） | 确认不是以 root 运行 |
| `app.tgz` | 应用载荷（容器编排文件、UI 配置、图标等），再套一层压缩 | 想深挖就 `tar -xzOf rustfs-fnos-1.0.4-x86.fpk app.tgz \| tar -tzf -` 看清单 |
| `wizard/` | 安装向导的表单定义 | 决定了安装时问哪些字段 |
| `ICON.PNG` / `ICON_256.PNG` | 应用图标（64 / 256） | 文件名是大写的，这是打包工具的硬要求 |

**看到这些就说明有问题**（正常包不该有）：

- `.env`、`config.env`、`*.pem`、`*.key`、`id_rsa` 之类的凭据文件；
- `.DS_Store`、`*.bak`、`*~` 这类编辑器/系统垃圾；
- `cmd/` 里出现你没预期的大段代码，尤其是往外发数据、下载并执行远程脚本、修改 `/etc` 的内容。

想确认包会做什么，最直接的办法是读 `cmd/` 下的脚本。它们不做隐藏动作，也不应该包含网络上传逻辑。

## 五、`manifest.version` 与 Release tag 的关系

规则很简单，一一对应：

| Release tag | `manifest` 里的 `version` | 包文件名 |
|---|---|---|
| `v1.0.4` | `1.0.4` | `rustfs-fnos-1.0.4-x86.fpk` |
| `v1.0.4-1` | `1.0.4-1` | `rustfs-fnos-1.0.4-1-x86.fpk` |

也就是：**tag 去掉开头的 `v`，就等于包里的版本号**。

自己核对的方法：

```bash
# 从包里读出版本号
tar -xzOf rustfs-fnos-1.0.4-x86.fpk manifest | grep -E '^\s*(appname|version|platform)\s*='
```

期望看到（注意打包后等号两侧空格会被去掉）：

```
appname=rustfs-fnos
version=1.0.4
platform=x86
```

- `appname` 必须是 `rustfs-fnos`——如果变成了别的名字，说明这不是本项目的包；
- `version` 必须与 Release tag 一致；
- `platform` 必须是 `x86`（当前只发布 x86）。如果你在 ARM 设备上装到的包写着 `x86`，那就装错了。

## 六、版本号为什么有 `x.y.z` 和 `x.y.z-N` 两种

| 形态 | 什么时候用 | 例子 |
|---|---|---|
| `x.y.z` | 跟随上游 RustFS 的正式版本 | 上游发 1.0.4 → 本包发 `1.0.4` |
| `x.y.z-N` | 上游没变，只改了我们这层（脚本、端口默认值、文档） | `1.0.4-1`、`1.0.4-2` |

没有第三种形态。打包工具只接受这两种；`1.0.4-beta`、`v1.0.4`、`1.0.4-rc1` 这类写法会在构建时直接失败（`-` 后面必须是整数）。所以如果你在某个渠道看到这种版本号的包，它一定不是本仓库发布的。

---

## 七、一句话总结

**下载 → 算 SHA256 → 和 `SHA256SUMS` 与 Release 正文比 → 三个值一致才装。**
除此之外的"看起来没问题"都不算验证。

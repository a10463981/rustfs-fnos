# 数据目录的权限：为什么通常**不需要** sudo

> **状态：已定案（v9）。** 之前的说法「用户自建目录必须先 `chown` 一次」是**错的**——真机已证明 fnOS 会把权限授好，是我们自己的检查把它判死了。本节是当前事实与处理办法。

---

## 一、fnOS 的 TrimACL：目录属主是别人，应用也能写

fnOS 在存储卷上挂了一层访问控制（挂载项 `trimacl`，权限以扩展属性 `system.trim_acl` 记录）。它会给**具体的应用用户**单独授权，而不是只靠传统的 owner/group/other 三段。

真机上看到的样子（`192.168.100.64`，包用户 UID 996）：

```text
# 文件管理器里由 admin 建的空目录：属主是 admin，权限看起来是 0
$ ls -ldn /vol1/1000/RustFS
d--------- 2 1000 1001 /vol1/1000/RustFS

# 但包用户真的能往里写（实测）
$ sudo setpriv --reuid 996 --regid 990 --clear-groups touch /vol1/1000/RustFS/probe
（成功）
```

原因：TrimACL 给 `uid:996` 挂了一条 `rwxpdDaAeEc` 的允许项。所以：

- **「属主不是应用用户」≠「不能写」** —— 在 fnOS 上这是常态；
- **加不加 `Users` 组，对这类目录的写入没有影响**（实测：不加组也能写）。所以 `config/privilege` 里的 `join-groups` **不是**「免 sudo」的依据，只为兼容「组可写 775」的老式共享目录，留着无害；
- 因此 v9 起，判断标准从「看属主」改成了「**以应用身份真的写一次**」（`probe_writable`）。

### 自己查一下某目录的授权

```bash
# 看挂载项里有没有 trimacl
mount | grep -w trimacl

# 看某个目录的 TrimACL 条目（需 root）
sudo /usr/trim/bin/trimacl /vol1/1000/RustFS

# 传统 POSIX ACL（fnOS 上通常为空，没有扩展条目）
sudo getfacl /vol1/1000/RustFS 2>/dev/null
```

> `trimacl` 命令的完整用法与 `system.trim_acl` 的取值语义**需核实**（上面是从真机用法反推的）；本文只依赖一条已被实测的事实：**应用用户 uid 出现在 `<allow>` 条目里，就能写。**

## 二、所以：什么时候**不需要** sudo

**绝大多数情况：不需要。**（与 `docs/data-location.md` 的口径一致：默认预期是「直接用」，例外只有下面第三节那两种）

在「文件管理」里新建一个目录 → 把路径填进安装向导 → 通常直接装成功。因为：

1. 平台/文件管理器建目录时会把这台机器上的应用用户一起授权（TrimACL）；
2. 应用的可写性检查是**真实写入**，不是比对属主。

---

## 三、什么时候**仍然**需要一次 `chown`

只剩三种（都会被明确拦下并给命令）：

| 情况 | 表现 | 处理 |
|---|---|---|
| 目录被显式设成「应用不可写」（例如你手动把权限改小、或平台没授权这个新目录） | 报「**成因A**：目录已存在，但以本应用身份（UID x、组 y）写不进去」 | 按提示执行 `sudo chown -R <uid>:<gid> <路径>` + `sudo chmod 750 <路径>` |
| 目标路径还不存在，且父目录不让应用写入（如直接写 `/vol1/xxx`，而 `/vol1` 本身只读） | 报「**成因B**：这个路径建不出来——父目录 … 不允许本应用写入」 | 按提示 `sudo mkdir -p` + `chown`，或换到自己的存储空间子目录 |
| 目录落在系统目录或其它应用目录（`/etc`、`/var`、`/vol1/@appdata/otherapp` …） | 被路径规则直接拒绝（与权限无关） | 换位置；这些位置**不该**放数据 |

> 提示里的命令都是**按你填的路径与这台机器的真实 uid/gid 拼好的**，直接复制执行即可，不含需要你自己替换的占位符。

## 四、安装/配置时的行为（v9）

| 时机 | 行为 |
|---|---|
| 安装前检查（`install_init`） | 以容器运行用户身份**真实写一个探针文件**，成功即放行；失败按成因 A/B 报错并给命令。日志里会记一行 `data-dir check … cur_uid=… target_uid=…` 便于排查 |
| 安装回调（`install_callback`） | 再以同样方式验一次（此时目录已建好），**不再比对属主**；属主不是应用用户但可写时打一行提示说明是 TrimACL 授权 |
| 改设置页（`config_init`/`config_callback`） | 同一套探测；只改指向、不搬数据；失败时说明「本次没有改动任何数据」 |
| root 环境下探测 | 若当前是 root 而容器用户不是 root，先 `setpriv --reuid <uid> --regid <gid> --clear-groups` 降权再写 —— **root 写什么都成功，用它探测等于没检查** |

## 五、如果你就是想让属主变成应用自己（可选）

不是必须的。只有在你想彻底摆脱「依赖平台授权」时才做：

```bash
# 在应用已安装、数据目录已存在的情况下（先停应用）
sudo chown -R <应用uid>:<应用gid> <数据目录>
sudo chmod 750 <数据目录>
```

查应用 uid/gid：`sudo -u rustfs-fnos id` 或 `ls -ldn /var/apps/rustfs-fnos`。

## 六、这份说明的边界

- 「TrimACL 会给应用用户授权」= **真机实测**（`/vol1/1000/RustFS` 属主 `admin:Users`、`uid 996` 可写、`test -w` YES、`setpriv` touch 成功）；
- 「是不是**每次**由文件管理器新建目录都会自动授权」= **尚未逐次证实**（我们只测了一个目录；ACE 也可能来自用户之前的操作）。所以仍然保留 A/B 两条命令作为兜底 —— 但**默认预期是「不需要 sudo」**；
- 「共享文件夹（用户可见共享）」的权限形态**未实测**（本机还没建共享），等有样本再补。

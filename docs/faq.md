# 常见问题（升级 / 拉镜像 / 状态异常）

## 为什么应用自己不能拉镜像？会不会是故障？

**不是故障，是 fnOS 平台的设计。**

本应用以专用包用户（`rustfs-fnos`）运行，而 fnOS 的镜像加速站要求请求里带一组签名头（`X-Meta-Sign` / `X-Meta-Token`）。这组签名头只会写进 **root 的** docker 客户端配置（`/root/.docker/config.json`），包用户读不到，因此：

- 包用户执行 `docker pull` 会**回落到直连 `registry-1.docker.io` 并超时**；
- 以 root 执行同样的 `docker pull` 是正常的（实测拉一个新 tag 需要 30 秒～1 分 20 秒）。

所以本应用**从不自己拉镜像**。它的做法是：

1. 启动或状态检查时，把「compose 里声明的镜像」和「容器实际在跑的镜像」做比对；
2. 发现不一致、且目标镜像**已在本地** → 自己重建容器并校验容器 id 真的换成了目标镜像；
3. 发现不一致、但目标镜像**还不在本地** → 登记一条「待校验升级」，等应用中心（以 root 运行）或管理员把镜像拉到本地后自动完成切换；
4. 超过宽限期（默认 15 分钟）仍未匹配 → 状态返回失败，并打印「目标/容器 id + 三步修复 + 回滚命令」。

你看到的最多是一句 `WARN`/`INFO`，不代表应用坏了。

## 升级后状态异常？先看是哪一种

### ① 网络不通（镜像站 / registry 都连不上）

- **你会看到**：`拉取失败归因：<镜像>` + `· 连通性：本机直连 registry-1.docker.io 不通（超时/无出口）`
- **含义**：这台机器当前出不了网，或镜像站不可达。
- **建议动作**：先确认 NAS 能上外网。判定方法：在**有外网的机器**上执行 `curl -I https://registry-1.docker.io/v2/`，正常会返回 `401`（不是超时）。网络恢复后由管理员执行 `sudo docker pull <镜像:tag>`，再在应用中心「停止 → 启动」。

### ② tag 不存在 / 打错了

- **你会看到**：`拉取失败归因：<镜像>` + `· tag 是否存在：脚本无法可靠区分（registry 直连不可用），请在能上网的机器上 docker manifest inspect <镜像:tag>`
- **含义**：镜像引用写错了，或上游根本没发这个 tag。
- **注意**：**脚本无法自动区分这一种与①** —— 两者在日志里都是同一条 `context deadline exceeded`（因为直连 registry 本身不通）。这是本应用的已知盲区，不是漏判。
- **建议动作**：到有外网的机器执行 `docker manifest inspect <镜像:tag>`；报 `no such manifest` 就是 tag 写错。这类问题**需要重新打包**（`manifest` 的 `version` 与 compose 的 `image:` 一起改，见 `docs/build.md` 的 `check-image-bump.sh`）。

### ③ 缺少签名头（包用户拉不了）

- **你会看到**：`本应用以包用户运行，没有 fnOS 镜像站的签名头……无法自行拉取——这是平台设计，不是故障。`
- **含义**：**正常现象**，不是错误。镜像会由应用中心（root）或管理员拉取。
- **建议动作**：什么都不用做，等 1–2 分钟；若仍不生效，按应用提示的三步走：
  1. `sudo docker images` 看有没有目标 tag；
  2. 没有就 `sudo docker pull <镜像:tag>`（管理员执行）；
  3. 再在应用中心「停止 → 启动」（`start` 会自动重建并校验）。

## 升级期间服务会中断吗？

会。容器重建（`up --force-recreate`）期间，S3 API（9200）与控制台（9201）都会短暂不可用，通常几秒到几十秒。**建议在维护窗口执行升级**。

---

## 回滚会还原什么？

只还原**镜像引用**：把 compose 的 `image:` 行改回上一版并重建容器。**不会**还原端口、环境变量、数据目录路径等其它配置——如果新包除了镜像之外还改了这些，回滚后得到的是「旧镜像 + 新配置」的混合体，需要人工核对。

回滚依赖两样东西：

- `@appconf/<app>/previous_image`（升级流程触发时由 `upgrade_init` 写入，取的是**容器实际在用的**那个引用）；
- 上一版镜像仍在本地。

如果这次是「启动/状态检查时发现漂移」（而不是升级流程触发），应用没有记录上一版镜像，日志里会直接告诉你用哪个值回滚、或者让你用 `sudo docker images` 自己找——不会留空。

## S3 API 端口能改吗？改完要注意什么？

**能改，安装时和装好之后都能改。**

- 安装向导 →「端口与运行参数」→ **S3 API 端口**（默认 `9200`）；同一页下面还有**Web 控制台端口**（默认 `9201`）。
- 装好之后：应用中心 → 该应用 → 设置 → 同一个位置也能改。

改端口时的四条须知：

1. **两个端口不能相同**，也不能被别的程序占用（安装/保存时会检查，占用会直接报错并告诉你哪个进程在监听）。
2. **改的是宿主机对外那个号，容器内部一直是 9000/9001**，所以不需要动任何应用配置。
3. **改了 S3 API 端口，所有连着它的客户端都要跟着改**（备份软件、媒体库、`aws-cli` 的 `--endpoint-url`），否则会连不上。
4. **改端口会重建容器**，服务中断十几秒。数据不受影响。

端口优先级（排查时用）：**设置页/向导填的值 → `settings.env` 里的 `API_PORT` → 平台的 `TRIM_SERVICE_PORT` → `9200`**。
真正的生效方式是：写完设置后，把端口**渲染进 compose 的 ports 行**再重建容器 —— 因为 compose 读不到我们的 `settings.env`，也不保证拿得到向导变量，靠变量插值会让用户改的端口静默失效。

## 桌面图标是怎么打开的？为什么要在窗口内而不是新标签？

**现在点图标会直接在飞牛 fnOS 的窗口里打开 RustFS 控制台**（不再新开浏览器标签）。这一节讲清它是怎么做到的，以及它依赖什么——因为这条路只在特定条件下成立，值得你知道。

### 原理：fnOS 的「窗口内打开」不是简单塞一个 iframe

fnOS 里让应用在窗口内打开的入口（`type: iframe`）**不是**直接把 `http://<NAS>:<端口>` 塞进一个 iframe，而是加载平台自己的路径 `/app/<应用名>/…`，再由平台网关转发给**应用自己提供的 unix socket**。

所以一个应用要在窗口内打开，需要同时具备三样：

1. 应用目录下有一个 `app.sock`（`gatewaySocket`，相对「应用根」）；
2. 入口里声明 `gatewayPrefix: /app/<应用名>`、`gatewaySocket: app.sock`、`port: ""`；
3. 应用自己能把平台转来的请求处理掉（含它带来的路径前缀）。

### 我们怎么做的

RustFS 官方镜像只监听 TCP，不提供 unix socket，所以本应用多了一个**极小的 nginx 容器**（`rustfs-fnos-gateway`，镜像 `nginx:1.27-alpine`）专门干这件事：

```
fnOS 平台网关  →  /vol1/@appcenter/rustfs-fnos/app.sock  →  http://rustfs:9001（控制台）
```

同时给 RustFS 设了上游自带的开关 **`RUSTFS_CONSOLE_PREFIX=/app/rustfs-fnos`**，让控制台页面与它的静态资源都挂在 `/app/rustfs-fnos` 这个前缀下——这样两边路径才对得上。

**实测结果**：窗口内正常打开；控制台直连地址变成 `http://<NAS>:<控制台端口>/app/rustfs-fnos/`，**旧地址 `/rustfs/console/` 会返回 403**（这是正常的，前缀换了）。

### 所以你会看到

| 场景 | 表现 |
|---|---|
| 点桌面图标 | 在 fnOS 窗口内打开控制台 ✅ |
| 浏览器直连控制台 | 用 `http://<NAS>:<控制台端口>/app/rustfs-fnos/`（旧路径 403） |
| S3 API | 不受影响，仍是 `http://<NAS>:<S3端口>` |

### 已知限制（都实测过）

| 限制 | 说明 |
|---|---|
| **多一个容器** | 应用会额外运行 `rustfs-fnos-gateway`（nginx，约 48 MB 镜像）。它只做转发，不存数据 |
| **它挂了只影响「窗口内打开」** | gateway 停止/异常时，点图标打不开控制台，但 S3 API 与「浏览器直连控制台地址」都照常可用。`status` 对这种情况只记警告、不会把应用判成故障 |
| **依赖上游的前缀开关** | 如果 RustFS 未来去掉了 `RUSTFS_CONSOLE_PREFIX`，这条路会失效，需要回退到「新标签打开」 |
| **镜像多一个来源** | 除 RustFS 官方镜像外，还依赖 `nginx:1.27-alpine`（见 `docs/licensing.md`） |

> 如果你在某个 fnOS 版本上发现点图标打不开：先在浏览器直接开 `http://<NAS>:<控制台端口>/app/rustfs-fnos/`——能开说明服务没问题、是窗口这条路的问题（看 `docker logs rustfs-fnos-gateway`）；打不开就是服务本身的问题。

## 窗口内打不开、或者打不开后登录失败，怎么办？

分三种情况，按顺序排查——三种都实测过。

### ① 窗口内是空白 / 报 Bad Gateway

这说明「窗口」这一层没接上，与服务本身无关。先验证服务：

```bash
# 在 NAS 上执行
curl -o /dev/null -w '%{http_code}\n' http://127.0.0.1:<控制台端口>/app/rustfs-fnos/
# 200 = 服务正常，问题在窗口这条路
```

- 返回 **200** → 看转发容器：`docker logs rustfs-fnos-gateway`。它是窗口内打开专用的转发组件；
- 返回 **403** → 前缀没生效（控制台还挂在旧路径），多半是镜像版本或 env 没生效，重启应用；
- 连不上 → 服务本身的问题，先看 `docker logs rustfs-fnos`。

### ② 窗口能打开，但登录一直失败

**正常情况下你不需要填任何东西** —— 从 v17 起，窗口内打开时页面会**自动**把正确的服务器地址写进浏览器，直接输账号密码即可。
只有两种情况才需要手填：**你换了访问地址**（IP、域名、http/https 任一变化），或者**清过浏览器数据**（localStorage 被清空）。（原理见本节末尾 ④。）

如果仍然失败，那就是**自动填的地址与你实际用的访问地址不一致**。这时看登录页的第三个框「服务器地址」：

RustFS 控制台是纯前端应用，登录页除了账号、密码，还有一个**服务器地址**输入框，默认值是 `http://localhost:9000` —— 那是「**你自己这台电脑**的 9000 端口」，永远连不上。

| 字段 | 填什么 |
|---|---|
| 服务器地址 / Server address | `http://<NAS地址>:<S3 API 端口>`，例如 `http://192.168.1.10:9300` |
| 账号 / Access Key | 安装时设的管理员账号 |
| 密码 / Secret Key | 安装时设的密码 |

两个常见填错：
- **填成控制台端口**（9301 之类）—— 那是网页端口，不是 S3 API；
- **填成 `localhost` 或 `127.0.0.1`** —— 那指的是你打开浏览器的那台电脑。

填对一次就会被浏览器记住（存在 localStorage），以后不用再填。

### ③ 服务器地址填对了，还是失败

那就是 **CORS（跨源）**。原因是：窗口内页面的来源是「你访问 fnOS 的地址」（例如 `http://192.168.1.10:5666`），而登录请求要发到 S3 API 端口（`9300`）—— 端口不同就是**跨源**，浏览器会先检查 S3 那边有没有允许这个来源，没有就丢弃结果，页面只显示「登录失败」。

**症状特征**：点登录后，转发容器 `docker logs rustfs-fnos-gateway` 里**一条 POST 都没有**（因为那条请求根本不经过网关，是浏览器直连 S3 端口的）。

**修法**：应用中心 → 本应用 → 设置 → 「**允许访问的来源**」填你实际访问 NAS 用的地址：

```
http://192.168.1.10:5666
```

要点：
- 必须与**浏览器地址栏里的协议+主机+端口完全一致**（`http` vs `https`、IP vs 域名、端口号都算）；
- 用域名访问就填域名，用 IP 就填 IP；两种都用就逗号分隔；
- **留空 = 允许所有来源**（最省事，但任何网站都能发起无凭据的跨源请求，安全性略低）；
- 改完会**重建容器**（几秒不可用），数据与凭据不受影响。

### ④ 附：为什么以前要手填，现在不用了

控制台是纯前端应用，登录页那个「服务器地址」的取值顺序是：

1. 浏览器里记住的地址（`localStorage`）；
2. 编译时写死的默认值（**运行时改不了**，我们试过，无效）；
3. 兜底 `http://localhost:9000` —— 那是**你自己这台电脑**，永远连不上。

以前从浏览器新标签打开时，页面就是控制台本身（同源），你登过一次它就记住了；
改成「窗口内打开」后，页面的来源变成 fnOS 自己的地址，是**另一个来源**，读不到那份记录 → 落回 `localhost` → 登录失败。

v17 起，转发组件会在首页 HTML 里注入一段极小的脚本，**替你**把地址写上（只在「还没设过」时写，不会覆盖你自己填的）。所以你不用管它。

**什么时候还需要手填**：只有**换了主机名**时才需要——比如从 IP 换成域名、或者换成另一台 NAS 的地址。这时脚本**故意不覆盖**（你可能就是想指到别处），你手填一次即可。

**重装或改了端口之后，为什么以前要手动清一次？**（v17.2 起已修）

浏览器把这条地址按「**站点（协议 + 主机 + 端口）**」持久保存。旧版本只在「**完全没有值**」时才写，
于是重装后端口变了（比如从 9300 变成 9200），旧值还在，脚本就一直跳过 —— 表现就是「每次重装都要进设置里清一次地址才可用」。

v17.2 起改成按**主机名**判断，规则只有三条：

| 你浏览器里已存的地址 | 脚本怎么做 | 什么时候遇到 |
|---|---|---|
| 没有值 | **写入**当前正确的地址（`http://<当前主机>:<API端口>`） | 换浏览器、清过站点数据 |
| **同一台 NAS，端口变了** | **自动覆盖成新端口** | **重装、改端口——只需刷新一次页面，不用手清** |
| **指向另一台机器 / 另一个域名** | **不动** | 你故意指向别处的场景，我们不擅自改 |
| 值坏了（解析不了） | 覆盖成当前正确值 | 极少见 |

所以：**重装或改端口后，刷新一次页面就会自动纠正；只有当你把地址指向另一台主机/域名时，才需要手填一次。**

> 想自己确认注入是否生效（**必须走网关 socket，别用控制台端口**）：
>
> ```bash
> sudo curl -sS --unix-socket /vol1/@appcenter/rustfs-fnos/app.sock \
>   http://localhost/app/rustfs-fnos/ | grep -c 'rustfs-server-host'
> ```
>
> 返回 **≥1** 说明注入成功；**0** 说明没生效（此时按上表手填一次即可，不影响使用）。
>
> **为什么不能直接 `curl http://<NAS>:<控制台端口>/...`**：那个端口是 RustFS 容器自己的端口，
> 请求**不经过转发组件**，自然也就看不到注入 —— 用它检查永远是 0，会把人带偏。
> 注入只在「平台网关 → `app.sock` → 控制台」这条链路上生效。

### ⑤ 永远可用的兜底：直连控制台

不想折腾窗口这条路时，直接在浏览器打开：

```
http://<NAS地址>:<控制台端口>/app/rustfs-fnos/
```

这条路**不经过平台网关**，也不受 CORS 影响（同源），任何时候都能用。

## 怎么把数据改到自己的存储空间？（两步）

> **要改数据目录，请按两步走（顺序不能反）：**
> 1. **先到「应用设置 → 访问权限」把这个目录添加/授权**给本应用；
> 2. **再回到「运行设置 → 数据存放位置」**选「改到下面填写的目录」，填**同一个路径**并保存。
>
> 为什么必须先授权：fnOS 是按「应用用户」单独授权的（TrimACL），没授权时本应用写不进去，第 2 步就会报「数据目录不可写」。

补充两点：

- **安装时不用选目录**：从 1.0.4-1 起，安装向导里没有「数据目录」这一项，一律用默认位置；改目录只在「应用设置」里做。
- **改目录不搬数据**：切换后旧目录里的对象仍在原地，日志会给出旧路径与搬迁命令（见 [data-location.md](data-location.md)）。

### 如果第 2 步报「数据目录不可写」

几乎都是第 1 步没做或没生效。按顺序检查：

| 检查 | 说明 |
|---|---|
| 「访问权限」里**确实加了这个目录**吗 | 加完通常立即生效；路径要与第 2 步填的**完全一致**（大小写、末尾斜杠都算） |
| 目录是不是**你自己在「文件管理」里建的** | 是的话更要确认第 1 步已授权；fnOS 不会自动给已存在的目录补授权 |
| 指向的是不是**平台目录**（`/vol1/@appdata` 等） | 如果是，**不要改**——那是应用中心的目录，改了会波及其它应用。请换到普通存储目录 |

实在不行，最后手段（把目录交给本应用，然后重试第 2 步）：

```bash
sudo chown -R <报错里的UID>:<报错里的GID> /vol1/1000/你的目录
sudo chmod 750 /vol1/1000/你的目录
```

> 报错信息里已经带上了真实的 UID/GID、属主和权限，可以直接复制粘贴。

### 一句话记住

**先授权，再改路径。** 反过来必报「不可写」。

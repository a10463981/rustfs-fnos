# 常见问题

## 用户可见行为总表

先看这张表。左边是你遇到的情况，中间是你实际会看到什么，右边是该做什么。

| 行为 | 你会看到什么 | 该怎么做 |
|---|---|---|
| **升级期间服务中断** | 升级那几十秒里，控制台打不开、S3 客户端报连接失败 | 正常现象。挑没人用的时候升级；正在跑的备份先停掉 |
| **回滚只还原镜像** | 回滚后镜像回去了，但端口、数据目录、环境变量没跟着回去 | 回滚只负责「换回旧镜像」。配置错了要人工核对，别指望它自动复原 |
| **卸载会清除访问凭据** | 重装后所有接入过它的应用开始报 `403 InvalidAccessKeyId` | 卸载/重装前先列好接入方清单；重装后拿新 AK/SK 逐个改，改一个测一个 |
| **同一版本不能重装** | `appcenter-cli install-fpk` 直接说「已安装」；`install-local` 跑完凭据变了 | 升级**只用应用中心界面**。别用 `install-local`，那等于卸载重装 |
| **应用自己不能拉镜像** | 日志里「拉取失败 / 超时 / context deadline exceeded」 | 不是故障。`sudo docker pull <镜像:tag>`，成功后回应用中心「停止 → 启动」 |
| **镜像没换会被判失败** | 升级后等约 15 分钟，状态变成失败，日志里有一段「三步修复 + 回滚命令」 | 按日志做：拉镜像 → 「停止→启动」。应用会自己比对并重建容器 |
| **同 tag 重推检测不到** | 上游把同一个 tag 的内容换掉了，你这边看不出任何变化 | 对我们的意义是发布纪律：每次发版**必须换新 tag**，不要复用 |
| **改端口只动宿主侧** | 把 9200 改成 9300 后，只有 NAS 上对外那个端口变了 | 不用改应用配置、不用重启 NAS。告诉用 S3 的软件新端口就行 |
| **管理员账号密码是你自己设的** | 安装向导里让你当场填账号和密码，不是程序生成完再让你去文件里找 | 忘了就「配置/设置」里重设，或用 SSH 从应用配置目录读回（见 [install-fnos.md](install-fnos.md)）。卸载会清掉它，重装要重新填 |
| **数据放默认目录，还是自己选存储空间** | 默认落在应用自己的数据目录（通常在被应用占用的那个卷上，往往不大）；卸载或安装失败回滚时，这份数据可能被一起清掉 | 装的时候就把它指到**大容量存储空间**；已装好的可以在「配置/设置」里改（改完旧数据要自己搬，命令见 install-fnos.md「数据放哪里」）。这条比任何性能调优都重要 |
| **切换数据目录后，原来的桶不见了** | 换到自定义目录（或再换回默认）之后，控制台里是空的，原来建的桶读不到、`GetObject` 返回 404 | 换目录**不会搬数据**：原来的默认目录被改名成 `data.old-<时间戳>` 留在原地，**没有被删除**（实测：桶与对象都在，21,379 字节）。想搬回来：停应用 → `sudo cp -a /vol<N>/@appdata/<app名>/data.old-<时间戳>/. /vol<N>/@appdata/<app名>/data/` → `chown` → 启动；完整命令见 [data-location.md](data-location.md) |
| **卸载重装后起不来 / 一直等待** | 装完没有控制台、`status` 不为 0；日志里出现「拉取失败 / 超时」，或等约 15 分钟后状态变失败 | 实测：**卸载会把应用用的镜像 tag 一起移除**（`rustfs/rustfs:<版本>` 那个名字没了），重装要找它就得重新拉；而应用自己拉不动（平台限制）。处理：`sudo docker pull rustfs/rustfs:<版本>` → 应用中心「停止 → 启动」。所以重装前最好先记下版本号 |
| **安装/升级失败后数据没了** | 应用中心提示安装失败；之后 `/vol1/@appdata/<app名>/data` 整个不存在，重启也没用，凭据文件也不见了 | 平台在「应用初始化」阶段失败后会执行失败回滚，把本应用的数据目录与配置目录一起删掉 —— 不是本应用删的，也拦不住。**升级前先备份**（README「升级前必做」给了 30 秒命令），失败后用备份恢复。注意：这条只在我们实测过的那条路径上被确认；「应用中心升级失败是否同样回滚」尚未确认，按最坏情况准备 |
| **命令行 `install-local` 报 `10237 … permission denied`** | `code 10237: fork/exec /tmp/appcenter.pack.<reqid>/cmd/install_init: permission denied` | 该命令会把**源码目录**复制到临时目录后执行，而源码目录权限是 700，包用户进不去、也执行不了脚本（从 `.fpk` 安装时平台会把脚本规范化成 755，所以不会踩）。**改用应用中心「手动安装」上传 `.fpk`**；另外 `install-local` 的语义是卸载再装，会换凭据 |

一句话记法：**「拉不到镜像」找 root，不怪应用；「升级」走界面，不碰命令行；「卸载」会换密码，先想清楚再点。**

## 为什么应用自己不能拉镜像？会不会是故障？

**不是故障，是 fnOS 平台的设计。**

本应用以专用包用户（`rustfs-fnos`）运行，而 fnOS 的镜像加速站要求请求里带一组签名头（`X-Meta-Sign` / `X-Meta-Token`）。这组签名头只会写进 **root 的** docker 客户端配置（`/root/.docker/config.json`），包用户读不到，因此：

- 包用户执行 `docker pull` 会**回落到直连 `registry-1.docker.io` 并超时**；
- 以 root 执行同样的 `docker pull` 是正常的（实测拉一个新 tag 需要 30 秒～1 分 20 秒）。

所以本应用**从不自己拉镜像**。它的做法是：

1. 启动或状态检查时，把「compose 里声明的镜像」和「容器实际在跑的镜像」做比对；
2. 发现不一致、且目标镜像**已在本地** → 自己重建容器并校验容器 id 真的换成了目标镜像；
3. 发现不一致、但目标镜像**还不在本地** → 登记一条「待校验升级」，等应用中心（以 root 运行）或管理员把镜像拉到本地后自动完成切换；
4. 超过宽限期（默认 15 分钟）仍未匹配 → 状态返回失败，并打印「目标/容器 id + 三步修复 + 回滚命令」。

你看到的最多是一句 `WARN`/`INFO`，不代表应用坏了。

## 升级后状态异常？先看是哪一种

### ① 网络不通（镜像站 / registry 都连不上）

- **你会看到**：`拉取失败归因：<镜像>` + `· 连通性：本机直连 registry-1.docker.io 不通（超时/无出口）`
- **含义**：这台机器当前出不了网，或镜像站不可达。
- **建议动作**：先确认 NAS 能上外网。判定方法：在**有外网的机器**上执行 `curl -I https://registry-1.docker.io/v2/`，正常会返回 `401`（不是超时）。网络恢复后由管理员执行 `sudo docker pull <镜像:tag>`，再在应用中心「停止 → 启动」。

### ② tag 不存在 / 打错了

- **你会看到**：`拉取失败归因：<镜像>` + `· tag 是否存在：脚本无法可靠区分（registry 直连不可用），请在能上网的机器上 docker manifest inspect <镜像:tag>`
- **含义**：镜像引用写错了，或上游根本没发这个 tag。
- **注意**：**脚本无法自动区分这一种与①** —— 两者在日志里都是同一条 `context deadline exceeded`（因为直连 registry 本身不通）。这是本应用的已知盲区，不是漏判。
- **建议动作**：到有外网的机器执行 `docker manifest inspect <镜像:tag>`；报 `no such manifest` 就是 tag 写错。这类问题**需要重新打包**（`manifest` 的 `version` 与 compose 的 `image:` 一起改，见 `docs/build.md` 的 `check-image-bump.sh`）。

### ③ 缺少签名头（包用户拉不了）

- **你会看到**：`本应用以包用户运行，没有 fnOS 镜像站的签名头……无法自行拉取——这是平台设计，不是故障。`
- **含义**：**正常现象**，不是错误。镜像会由应用中心（root）或管理员拉取。
- **建议动作**：什么都不用做，等 1–2 分钟；若仍不生效，按应用提示的三步走：
  1. `sudo docker images` 看有没有目标 tag；
  2. 没有就 `sudo docker pull <镜像:tag>`（管理员执行）；
  3. 再在应用中心「停止 → 启动」（`start` 会自动重建并校验）。

## 升级期间服务会中断吗？

会。容器重建（`up --force-recreate`）期间，S3 API（9200）与控制台（9201）都会短暂不可用，通常几秒到几十秒。**建议在维护窗口执行升级**。

---

## 回滚会还原什么？

只还原**镜像引用**：把 compose 的 `image:` 行改回上一版并重建容器。**不会**还原端口、环境变量、数据目录路径等其它配置——如果新包除了镜像之外还改了这些，回滚后得到的是「旧镜像 + 新配置」的混合体，需要人工核对。

回滚依赖两样东西：

- `@appconf/<app>/previous_image`（升级流程触发时由 `upgrade_init` 写入，取的是**容器实际在用的**那个引用）；
- 上一版镜像仍在本地。

如果这次是「启动/状态检查时发现漂移」（而不是升级流程触发），应用没有记录上一版镜像，日志里会直接告诉你用哪个值回滚、或者让你用 `sudo docker images` 自己找——不会留空。

## 五、升级后版本号没变，是不是没升级成功？

**先别重装。** 按这个顺序判断，三步之内基本能定位。

### 第一步：确认容器到底在跑哪个镜像

```bash
# 容器名以实际为准（一般包含应用名）
sudo docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'
```

把它和 Release 说明里写的镜像 tag 对比：

- **一致** → 已经升级成功，你看到的「版本号没变」可能是应用中心缓存或看的是别的字段，刷新页面再看。
- **还是旧的** → 继续第二步。

### 第二步：看目标镜像在不在本地

```bash
sudo docker images | grep rustfs
```

- **目标 tag 不在** → 镜像还没到设备上。这是最常见的情况。执行：

  ```bash
  sudo docker pull <目标镜像:tag>
  # 成功后回应用中心「停止 → 启动」
  ```

- **目标 tag 在**，但容器还是旧的 → 回应用中心「停止 → 启动」一次。应用会在启动时发现「配置里写的是新镜像、容器跑的是旧镜像」，自己重建容器并校验。

### 第三步：看应用状态与日志

应用的判断逻辑是：升级后持续比对「配置声明的镜像」和「容器实际运行的镜像」，**宽限期 15 分钟**（按真实时间算，不是按检查次数）。

- 宽限期内：状态可能仍显示正常，同时后台在等镜像到位。
- 宽限期到：状态返回失败，日志里写清目标镜像 id、容器镜像 id、三步修复步骤，以及回滚命令。

日志位置（生命周期脚本写的那份）：

```bash
# 应用配置目录下的历史与待校验记录（实际文件名以设备为准）
sudo ls -l /var/apps/rustfs-fnos/etc/
sudo tail -50 /var/log/apps/rustfs-fnos.log 2>/dev/null
```

### 为什么它不自己把镜像拉下来？

因为它拉不了 —— 见本文前面「为什么应用自己不能拉镜像」那一节。应用能做的只是「比对 + 重建 + 告诉你怎么办」，拉镜像这一步必须由 root（应用中心或你 `sudo`）完成。

### 什么时候才该考虑重装

只有这几种情况：拉镜像一直失败且网络确认没问题、或者状态失败且日志给的修复步骤都试过。**重装会换凭据**（见本文「卸载重装后客户端全报 403」那一节），代价比你想的大，能「停止→启动」解决的就别重装。

## 六、卸载重装后，客户端全报 `403 InvalidAccessKeyId` 怎么办？

### 发生了什么

卸载应用时，它的配置目录（含 Access Key / Secret Key）被一起删掉了。重装会生成**全新的一组**凭据。旧凭据立即失效，于是所有还在用旧凭据的客户端统一报错：

```
403 Forbidden
InvalidAccessKeyId
```

这不是 bug，是设计如此：凭据属于应用配置，不属于数据，所以「保留数据」不会保留凭据。

### 怎么办

1. 到应用的控制台里，或用 SSH 从配置目录读出新凭据（读法见 [install-fnos.md](install-fnos.md) 第十一节）。
2. 把每个接入方逐个改成新凭据。最小验证命令：

   ```bash
   AWS_ACCESS_KEY_ID='新AK' AWS_SECRET_ACCESS_KEY='新SK' \
     aws --endpoint-url http://<NAS地址>:9200 s3 ls
   ```

3. 改完一个测一个，别一次改十个再一起试 —— 出错时不知道是哪个配错了。

### 下次怎么避免

卸载/重装前，先把接入方清单写下来：哪台机器、哪个应用、哪个备份任务在用这组凭据。这件事花五分钟，能省掉事后半天的排查。

## 七、升级到底会不会影响正在跑的备份？

**会。** 升级要重建容器，重建期间 S3 API（9200）不可用，通常是几秒到几十秒（镜像已在本地时快，需要现拉时慢）。

正在上传的对象大概率会失败，客户端一般会重试；但如果你的备份工具不重试，那个时间点的任务就算失败了。所以：

- 升级挑没人用的时候做；
- 或者先手动暂停备份任务，升级完确认服务正常再恢复。

**升级不会丢数据** —— 桶与对象在数据目录里，不在容器里。但「升级不丢数据」不等于「升级不影响业务」，这两件事都要知道。

## 八、为什么我不该用 `appcenter-cli install-local`？

因为它叫「安装」，实际做的是**卸载再安装**。对已经装着的应用跑它，会发生：

1. 应用被卸掉（配置目录、凭据一起没了）；
2. 重新装上，生成**新的** Access Key / Secret Key；
3. 所有接入方开始报 `403`。

对已安装应用，`appcenter-cli install-fpk` 则会直接返回「已安装」，什么也不做——所以它也不能用来升级。

**要升级就只用应用中心界面的上传新包/升级入口。** 它走的是应用的升级流程：先记录当前镜像、备份配置，再按新包重建容器，凭据保持不变。

---

## 九、我改了端口，需要改应用里的配置吗？

**不需要。**

你在向导里改的是**宿主侧**端口，也就是「NAS 上的哪个口对外」。容器内部一直监听它自己的固定端口（9000 用于 S3 API、9001 用于控制台），没有变。

所以：

- 不需要改应用配置文件；
- 不需要重启 NAS；
- 只需要把新的宿主端口告诉要连它的软件（以及你自己书签里的控制台地址）。

## 十、为什么发版必须换新 tag？

这是给自行发布的人的提醒，普通用户可跳过。

我们判断「镜像有没有换」的办法，是比较 compose 文件里写的镜像**引用字符串**和容器实际在跑的镜像。如果上游把同一个 tag 的内容重新推了一遍（tag 没变、digest 变了），字符串完全一样，我们**检测不到**任何变化。

所以发布纪律是硬性的：**每次发版必须用一个新 tag**（例如 `1.0.4` → `1.0.5`），不要复用旧 tag。这是已知盲区，不是可以靠脚本补上的漏洞。

构建侧还有一个对应的检查（版本变了但镜像没变就拦下来），见 [build.md](build.md)。

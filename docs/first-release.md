# 首次空跑：从建仓到「NAS 上真的能用」的 8 步

> 读者是项目维护者本人（不是普通用户）。目标：在一个空仓库上把「推代码 → CI 出包 → 打 tag → Release → 下载校验 → NAS 装上」整条链路走通一次。
>
> **为什么必须先空跑**：这条链路上有 4 个我们无法在本机验证的外部环节（runner 下载 fnpack、token 写权限、environment 审批、Release 资产下载）。把它们一次性暴露在一个 `v0.0.x` 或首个正式 tag 上，比暴露在「用户已经下载了坏包」之后便宜得多。
>
> 记号：🟢 只读 ｜ 🟡 有副作用 ｜ 🔴 危险 ｜ 需核实 = 没有权威依据，别当结论。

---

## 步骤 1 · 建 public 仓库

| 项 | 内容 |
|---|---|
| 做什么 | 在 GitHub 建一个仓库，**可见性必须选 Public** |
| 在哪做 | GitHub 网页 → New repository，或在已有本地仓库里 `gh repo create <owner>/rustfs-fnos --public --source=. --remote=origin` |
| 成功判据 | 仓库页能匿名打开；`git remote -v` 里能看到 origin；未登录浏览器访问仓库页不是 404 |
| 失败先看什么 | 建成了 Private → Release 资产就下不了（见下）；组织策略限制建 public 仓库 → 找组织管理员开权限 |

### 为什么必须 public（这条不能妥协）

**私有仓库的 Release 资产不能匿名下载。** 资产的访问权限跟着仓库可见性走，没有「仓库私有但资产公开」这种组合。

所以只要目标是「飞牛 NAS 用户都能下载」，就只有两条路：仓库 public，或另找分发渠道（对象存储/网盘/自有源）。本项目选前者，因为本仓库里没有任何需要保密的东西——它是纯打包层（配置、脚本、文档），上游 RustFS 是 Apache-2.0 开源代码。

> 顺带一个正面的副作用：public 仓库意味着别人能 fork 自查，README 里「如何自己构建」因此更有意义。

## 步骤 2 · 落盘仓库树并首次 push

| 项 | 内容 |
|---|---|
| 做什么 | 把 30 个文件放进本地目录，`git add -A && git commit && git push` |
| 在哪做 | 本地终端 |
| 成功判据 | `main` 分支上文件齐全；`deploy/fnos/manifest` 里 `version = 0.0.0`（**占位值，不是 1.0.4**）；GitHub 页面上能看到 `.github/workflows/` 下两个 yml |
| 失败先看什么 | 有文件没推上去 → 检查 `.gitignore` 是否误伤（`git check-ignore -v <file>`）；`version` 是 1.0.4 → 说明落的是旧版本骨架，改回 `0.0.0` 再推 |

**关键认知**：仓库里的 `manifest.version` 恒为 `0.0.0`，真实版本由 tag 在 CI 里注入。如果你手工把它改成 `1.0.4` 再提交，就等于有了两个版本真源，之后必然出现「包里的版本和 tag 对不上」。

## 步骤 3 · 触发 CI，看它是不是真的绿

| 项 | 内容 |
|---|---|
| 做什么 | 开一个 PR（或直接 push 一个空提交）触发 `fpk-ci` 🟡 |
| 在哪做 | GitHub → Actions 页面 |
| 成功判据 | ① run 绿 ② 日志里有 `runner 架构：x86_64` ③ 有 `Packing successfully.` ④ 有 `包内 version=0.0.0 ✓` ⑤ 预检输出 `FAIL=0 WARN=0` ⑥ Artifacts 里能下到 `.fpk` 且**大小非 0**（约 19 KB） |
| 失败先看什么 | 见步骤 4（下载 fnpack 失败）与下表 |

**失败分支速查**

| 日志里出现 | 原因 | 处理 |
|---|---|---|
| `下载 fnpack 失败` / 超时 / 连不上 `static2.fnnas.com` | 托管 runner 访问不到该域名 | **步骤 4**，三条退路选一条 |
| `fnpack sha256 不匹配` | 下到的不是二进制（比如 HTML 错误页） | 看日志里 `od -c` 打出的前几字节；确认 URL 与版本号；必要时 vendored 入库（步骤 4 退路 A） |
| `fnpack 版本不是 1.2.3` | 拿到了别的版本 | 同上。**不要**为了让它过就改成「取最新版」——不同版本打出的包 sha256 不同 |
| `fnpack build 失败（退出码 0，但按关键字判定为失败）` | 打包真的失败了，只是退出码仍为 0 | 往上翻日志找 `Required file ...` 之类；这条断言的存在意义就是防「假绿」 |
| 预检 `FAIL=1` | 结构/manifest/JSON/图标尺寸/硬编码有问题 | 看预检第几节报的，按节名定位 |
| `包内 manifest.version=... 期望 0.0.0` | stamp 没生效 | 检查 `scripts/stamp-manifest.sh` 是否被改动；这是「版本真源」的守卫，别绕过 |

## 步骤 4 · 第一道真实风险：CI 能不能下载到 `fnpack 1.2.3`

**这是整条流水线的第一个外部依赖，也是最可能第一次就红的地方。**

现状（如实说）：`https://static2.fnnas.com/fnpack/fnpack-1.2.3-linux-amd64` 我们**只在局域网环境验证过可下载**（HTTP 200，3,707,064 字节，ELF 静态链接，sha256 已记录）。**GitHub 托管的 runner 在公网上能否访问该域名、有没有地区/网络限制，尚未验证。** 这不是可以靠读文档解决的问题，只能跑一次看。

| 项 | 内容 |
|---|---|
| 做什么 | 观察步骤 3 的「安装 fnpack」这一步 🟢 |
| 成功判据 | 日志里有下载成功、sha256 校验通过、`fnpack --help` 输出含 `Version 1.2.3` |
| 失败先看什么 | 是 DNS 失败、TLS 失败，还是 403/404。三者处理方式不同（404 说明 URL/版本不对，不是网络问题） |

### 三条退路（按推荐顺序）

| 退路 | 做法 | 代价 | 什么时候选 |
|---|---|---|---|
| **A. vendored 二进制入库**（推荐） | 把 `fnpack 1.2.3 linux-amd64` 提交进仓库（如 `tools/` 下），CI 不再下载，直接用并校验 sha256 | 仓库多 ~3.7 MB 二进制；仓库不再是「纯文本」；需要一次单独评审（二进制入库是供应链决定，不能顺手做） | 首选。唯一不改变 CI 结构、也不依赖网络的办法 |
| **B. 换自托管 runner** | 在你自己的机器上跑 Actions runner，那台机器能访问 `static2.fnnas.com`（局域网内已验证） | 要一台常开机器 + 维护 runner + 凭据；机器安全边界变成你的责任；开源仓库用自托管 runner 跑来自 PR 的代码有额外风险（**需核实** GitHub 对公开仓库自托管 runner 的策略建议） | 只有确实需要内网依赖时才选 |
| **C. 本地出包 + 手工上传资产** | CI 只跑预检与断言，不打包；你在本地 `fnpack build`，手工 `gh release upload` 传 `.fpk` | 失去「构建可复现、来源可审计」的核心优势：用户下载的包不再由 CI 产出，`build-info.json` 也失去意义 | **最后选项**。只在 A/B 都不可行时用，且必须在 README 里如实说明「本包由维护者本地构建」 |

**不建议的做法**：让 CI 「先试下载、失败就用缓存/跳过」。那会让流水线在两种不同状态下都显示绿，等于把「这个包到底怎么来的」变成不确定。

> 无论选哪条，`FN_PACK_SHA256` 这个校验都不要去掉。sha256 是目前唯一能证明「跑的是我们审过的那个二进制」的东西。

## 步骤 5 · 打 `v1.0.4` tag

| 项 | 内容 |
|---|---|
| 做什么 | `git tag -a v1.0.4 -m "首发：RustFS 1.0.4 容器版" && git push origin v1.0.4` 🟡 |
| 在哪做 | 本地终端 |
| 成功判据 | GitHub 上能看到 tag；`fpk-release` workflow 被创建 |
| 失败先看什么 | tag 形态不对（`v1.0.4-beta`、`1.0.4`、`v1.0.4-rc1`）→ CI 会在版本格式断言处**立刻失败**，不会打出错版本的包。这是设计如此：`fnpack` 只接受 `x.y.z` 或 `x.y.z-<整数>` |

**打 tag 前确认两件事**：

1. `main` 上的代码是你想发布的那份（tag 会冻结当前 commit）；
2. 镜像 tag 与 `manifest.version` 是对应的 —— 这次是首发，两者都是 `1.0.4`；**以后每次发版必须同时换镜像 tag**（不要复用旧 tag，原因见下）。

> 为什么必须换新 tag：我们判断「镜像换没换」靠比较引用字符串，上游若把同一个 tag 重推了新内容（digest 变了），字符串没变，我们检测不到。这是已知盲区，只能靠发布纪律兜。

## 步骤 6 · 批准 `environment`，让 Release 真正发布

| 项 | 内容 |
|---|---|
| 做什么 | Actions → 该 run → Review deployments → Approve 🟡 |
| 在哪做 | GitHub → Actions → 进行中的 `fpk-release` |
| 成功判据 | 批准后 run 继续并变绿；Release 页面从 **Draft** 变成已发布；资产含 `.fpk` + `SHA256SUMS` + `build-info.json` |
| 失败先看什么 | ① 没有审批按钮 → `environment: release` 的保护规则没配好（**需核实**：所需审阅者/可部署分支这类配置项在各版本界面上的确切名称，以仓库 Settings → Environments 的实际界面为准）② 403 创建 Release 失败 → `GITHUB_TOKEN` 在本仓没有 `contents: write`，见下 |

**关于审批的设计意图**：Release 一旦发布就对所有人可见，撤回也留着下载记录。所以流水线是「先建 draft、资产传齐、人工点一下、才 publish」。这一步不是形式主义——它保证「资产不全会漏传」这类事故不会被外部看到。

**403 的两种处理**（需核实具体策略以你的仓库/组织设置为准）：

- 仓库 Settings → Actions → General 里把 Workflow permissions 调成允许写；
- 或改用 fine-grained PAT（单仓 + Contents 读写），存成 environment secret 并替换 workflow 里的 `GH_TOKEN`。

## 步骤 7 · 下载资产并校验

| 项 | 内容 |
|---|---|
| 做什么 | 从 Release 下载 `.fpk` 与 `SHA256SUMS`，本地校验 🟢 |
| 在哪做 | 任意一台机器 |
| 成功判据 | `sha256sum -c SHA256SUMS` 输出 `<file>: OK`；Release 正文里公布的 sha256 与之一致；`build-info.json` 里 `version=1.0.4`、`git_tag=v1.0.4` |
| 失败先看什么 | ① 匿名（不登录）下载 404 → 仓库不是 public（回到步骤 1）② 有资产但哈希不一致 → 传输问题或资产被替换，删掉重下 ③ `build-info.json` 里 `image.digest` 为 `null` → 正常，runner 上取不到 digest 时就是 null，不影响发布 |

**这一步要专门用「未登录的浏览器」试一次**：登录状态下能下载不代表别人也能下载，而这正是本项目分发的全部意义。

## 步骤 8 · 在 NAS 上装一次，跑通基本功能

| 项 | 内容 |
|---|---|
| 做什么 | 应用中心 → 手动安装 → 选刚下的 `.fpk` → 走向导 → 建桶 → 传文件 🟡 |
| 在哪做 | 一台干净的、非生产数据的 fnOS 设备上（x86） |
| 成功判据 | ① 装得上，桌面出现图标 ② 控制台打得开 ③ `curl :9200/health/ready` 返回 200 ④ 能建桶、能上传、能列出、能下载 ⑤ `main status` 返回 0 ⑥ 卸载时选「保留数据」，重新装回来数据还在（**但凭据会换，这是预期行为**） |
| 失败先看什么 | 见下表。另外：这一步发现的任何问题都应当**回滚到文档或骨架**，而不是在设备上手工修好就算完 |

**首次安装最可能卡的两处**

| 现象 | 原因 | 处理 |
|---|---|---|
| 控制台打不开、日志里有「拉取失败/超时」 | 应用是包用户，不能自己拉镜像（平台设计，签名头只在 root 的 docker 配置里） | `sudo docker pull rustfs/rustfs:1.0.4` → 应用中心「停止 → 启动」 |
| 启动失败，日志有 `permission denied` | 数据目录归属不对（容器以 UID/GID `10001` 运行） | `sudo chown -R 10001:10001 <数据目录>`，或重装让安装流程处理 |

装完之后**再走一遍步骤 8 的卸载**：确认「保留数据」确实保留了数据、凭据确实被清掉（重装后 `aws s3 ls` 用旧凭据应该报 `403 InvalidAccessKeyId`）。这是文档里对用户承诺的行为，得自己先验一次。

## 空跑完成后的三件事

1. **把环境与结果记下来**：runner 能否下载 fnpack（步骤 4）、审批是否生效（步骤 6）、匿名下载是否通过（步骤 7）。这三条都是文档里「需核实」的项，跑完就该改成结论。
2. **更新 `README.md` 的支持范围**：把实测通过的 fnOS 版本号填进去（现在是 TODO 占位）。
3. **删掉 tag 之前在 README/Release 里写的「未验证」字样**，但保留「已测环境 / 未验证环境」的区分 —— 别把「我测过一台」写成「支持所有版本」。

## 时间预期（诚实版）

| 阶段 | 顺利 | 需要处理步骤 4 的退路 |
|---|---|---|
| 步骤 1–2（建仓 + 落盘） | 20 分钟 | 同 |
| 步骤 3（首次 CI） | 10 分钟（等 runner） | — |
| 步骤 4（下载 fnpack） | 通过，无额外时间 | **+1～2 小时**（vendored 入库要单独评审并复核 sha256） |
| 步骤 5–7（tag → 审批 → 下载校验） | 20 分钟 + 等你点审批 | 同 |
| 步骤 8（NAS 安装回归） | 30 分钟 | 若卡权限/镜像，再 +30 分钟 |

**一天之内做完是现实的，前提是步骤 4 一次过。** 如果 CI 下载 fnpack 失败，不要在那个下午硬扛 —— 直接走退路 A（vendored 入库），它 20 分钟能改完，比反复试网络便宜。

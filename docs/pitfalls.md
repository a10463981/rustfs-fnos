# 踩坑总览（按症状检索）

> 适用范围：`rustfs-fnos`（RustFS 的飞牛 fnOS `.fpk` 封装）从 v0 到 `v1.0.4-2` 期间**真实发生过**的故障与误判。
> 组织方式：按「你看到了什么」检索，不按时间、不按模块。每条固定五段：**症状 → 根因 → 怎么确认 → 修法 → 状态**。
> 状态只有两种取值：**已修复**（当前版本不会再遇到）、**仍有边界**（现象可解释、有规避手段，但根因不在本项目手里，或只在特定条件下才不出现）。
> 本文只写发生过的事。没复现过的推测一律不进本文（推测请写在 issue 里）。

## A. 安装阶段：`10237`

> `10237` 是**同一个错误码对应至少四种不同根因**。看到它不要直接照搬上一次的结论，先按下面四条依次排除。

### P01 安装失败（`10237`）：应用用户不在 `docker` 组，摸不到 `docker.sock`
- **症状**：安装走到容器启动步骤后失败，返回 `10237`；手动以应用用户执行 docker 命令也会报权限不足。
- **根因**：`config/privilege` 以专用包用户（`run-as=package`）运行，而 `docker.sock` 属 `root:docker`；包用户不在 `docker` 组 → 无法 `docker create/start`。
- **怎么确认**：`id <应用用户>` 看输出里有没有 `docker` 组；`ls -l /var/run/docker.sock` 看属主与权限位。
- **修法**：在 `config/privilege` 的 `join-groups` 里加入 `docker`（用最小必要的组，不要顺手给 root）。
- **状态**：已修复。

### P02 安装失败（`10237`）：用 `install-local` 时源目录权限是 `700`
- **症状**：同样的包，`install-fpk` 能装；在源目录里 `appcenter-cli install-local` 就 `10237`。
- **根因**：安装器需要以其它身份读取源目录内容，源目录 `700` 时读不到，表现为安装阶段性失败。
- **怎么确认**：`ls -ld <源目录>`；换 `install-fpk <包路径>` 试同一次安装是否成功。
- **修法**：把源目录放宽到 `755`（至少让安装器可遍历），或改用 `install-fpk` 走已打好的包。
- **状态**：已修复（文档与流程规避）。

### P03 安装失败（`10237`）：安装任务内失败会触发平台 `rollback`，连数据一起清
- **症状**：安装中途失败，然后**数据目录也不见了**——上一步还在的文件，重试时没了。
- **根因**：平台对失败的安装任务执行 `rollback`，回滚范围包含 `@appdata/<app>`、`@appconf/<app>`，不只是 `target`。
- **怎么确认**：`ls -ld /vol*/@appdata/<app> /vol*/@appconf/<app>` —— 重试前后目录是否存在会变化。
- **修法**：把「可能失败」的检查（端口、依赖、镜像可拉取）全部提到**安装前**（`preflight` / `install_init` 前半段），让失败发生在写数据之前；已有数据先用 `scripts/backup-data.sh` 备份到共享目录。
- **状态**：仍有边界（`rollback` 是平台行为，本项目改不了；只能靠「失败前置」+ 备份规避）。

### P04 安装失败（`10237`）：全新机器 + 默认数据位置，安装前写探测判「不可写」
- **症状**：全新设备、数据位置保持默认（用户没改），安装直接失败；同样的包在「已经装过一次」的机器上正常。
- **根因**：平台在安装前还没创建 `@appdata/<app>`，而父目录 `/vol*/@appdata` 是 `root:root 755`；安装前的写探测按「当前用户能否在此写」判断 → 判为不可写。
- **怎么确认**：`ls -ld /vol*/@appdata`（注意属主是 `root:root`、`755`）与 `ls -ld /vol*/@appdata/<app>`（是否尚未存在）；二次安装是否必然成功。
- **修法**：对「目录由平台在安装过程中代建」这一情况做豁免——父目录可读、且目标子目录属于平台代建范围时，不因当前不可写而判失败。
- **状态**：已修复（「平台代建豁免」）。

## B. 打开入口：403 / Bad Gateway / 登录不上

### P05 点图标打开是一段 XML，`403`
- **症状**：桌面图标能点，窗口里显示一段 XML 错误，状态码 `403`。
- **根因**：入口 `url` 写成了 `/`，命中的是 S3 根路径（返回 XML 拒绝响应），而不是控制台页面。控制台真实路径是 `/rustfs/console/`。
- **怎么确认**：看 `app/ui/config` 里该入口的 `url` 字段；把该路径直接拼到访问地址后面看返回的是 HTML 还是 XML。
- **修法**：入口 `url` 指向 `/rustfs/console/`；网关前缀、`gatewayPrefix`、入口 `url` 三者保持同源同前缀。
- **状态**：已修复。

### P06 打开应用显示 `Bad Gateway`
- **症状**：入口可点，页面 `502 Bad Gateway`；`app.sock` 始终不生成。
- **根因**：网关侧车 nginx 以非 root 运行、容器内缺 `tmpfs` 可写目录，启动即 `[emerg] mkdir /var/cache/nginx ... failed`，随后无限重启，socket 从未被创建。
- **怎么确认**：`docker logs <网关容器>` 看是否有 `[emerg] mkdir`；`docker ps -a` 看该容器 `RestartCount` 是否持续增长；`ls -l ${TRIM_APPDEST}/app.sock` 是否存在。
- **修法**：给网关侧车容器挂可写的 `tmpfs`（覆盖 nginx 需要的临时/缓存目录），使其能在非 root 下完成初始化。
- **状态**：已修复。

### P07 窗口内打不开 / 能打开但登录失败：登录页「服务器地址」默认指向用户自己的电脑
- **症状**：控制台页面出来了，但登录必失败；浏览器控制台能看到请求打到 `http://localhost:9000`。
- **根因**：上游控制台登录页的「服务器地址」缺省值是 `http://localhost:9000` —— 在 NAS 场景下这指向**用户自己的电脑**，不是 NAS。
- **怎么确认**：浏览器开发者工具 Network 里看登录请求的目标域名/端口；对比 NAS 实际访问地址。
- **修法**：安装/启动时向控制台页面注入预置配置，把服务器地址填成当前访问的同源地址（不要求用户手填）。
- **状态**：已修复。

### P08 窗口内能打开但登录失败：S3 API 不发 CORS 头，浏览器直接丢弃跨源请求
- **症状**：页面正常、账号密码正确，但登录请求在浏览器侧失败，响应看起来「空」或直接报跨源错误。
- **根因**：S3 协议实现默认**不返回** `Access-Control-*` 响应头；控制台与 S3 API 不同源时，浏览器丢弃响应，与凭据是否正确无关。
- **怎么确认**：Network 面板看该请求是否被标为 CORS 错误；`curl -I -H 'Origin: <控制台地址>' <S3 地址>` 看响应里有没有 `Access-Control-Allow-Origin`。
- **修法**：让控制台与 S3 API 走**同一网关 origin**（同前缀 `/rustfs/`），从根本上不产生跨源请求，而不是去给 S3 加 CORS。
- **状态**：仍有边界（若用户绕过网关直连端口访问控制台，跨源问题会重新出现；这是使用方式问题，不是包的问题）。

### P09 试图用「前缀反代做同源」被 SigV4 判死
- **症状**：为绕开 CORS，给 S3 API 加一层路径前缀反代，结果所有签名请求 `SignatureDoesNotMatch` / `403`。
- **根因**：SigV4 的 canonical URI **参与签名计算**；反代改写了路径前缀，服务端按原始路径重算签名 → 必然不匹配。
- **怎么确认**：对比「直连端口」与「走前缀反代」的同一请求返回码；反代日志里能看到路径被改写。
- **修法**：不使用「改路径前缀」的方案做同源。同源要靠**同一 origin 下的不同路径由网关统一承载**（见 P08），或让控制台/API 保持同源直连。
- **状态**：已规避（该方案已作废，不要再试）。

## C. 升级与镜像

### P10 升级「成功」了，但版本号没变
- **症状**：`upgrade` 流程无报错，应用中心显示升级完成，容器里跑的还是旧版本。
- **根因**：`docker compose pull` **不走 daemon 的镜像加速配置**，在受限网络下拉取失败被静默跳过，随后 `up` 沿用本地旧镜像 → 表面成功、实际没换。
- **怎么确认**：比对 compose 里渲染出的 tag 与 `docker inspect` 里容器实际镜像的 tag/digest；`docker images` 看该 tag 的创建时间。
- **修法**：升级流程里显式核对「声明版本 ↔ 实际运行镜像」，不一致就显式重拉并重建容器；升级日志记录 digest。
- **状态**：仍有边界（`compose pull` 不走加速是平台事实，无法改变；只能靠显式校验兜住，且首次拉取仍需可用的镜像通道）。

### P11 应用用户拉不动镜像；而「2.6 秒拉完」其实是 cache hit
- **症状**：应用用户执行拉取失败或无网络；以 root 执行同样命令「瞬间成功」。
- **根因**：fnOS 镜像站的签名头只写在 `/root/.docker/config.json`，非 root 用户拿不到该凭据，无法直连 registry；「瞬间成功」是本地已有镜像层，不产生真实网络拉取。
- **怎么确认**：`id` 确认当前用户；`ls -l /root/.docker/config.json` 看是否仅 root 可读；把本地镜像先删掉再拉一次，看是否还「秒成」。
- **修法**：把需要联格拉取的动作放在特权阶段（`install_init` 等以 root 执行的环节）完成，或提前把镜像预热到设备上；不要指望应用用户能直连 registry。
- **状态**：仍有边界（属平台凭据模型，不可改）。

### P12 装完约 7 秒被判 `APP_CRASH`
- **症状**：安装后短时间正常，随后应用状态变为 `APP_CRASH`，但容器看起来在跑。
- **根因**：端口已渲染进 compose，但容器**没有被重建**，于是「compose 声明的端口 ≠ 容器实际发布的端口」，平台按端口探测判定崩溃。
- **怎么确认**：`docker inspect` 看容器实际 `PortBindings` 与 compose 渲染结果是否一致；`docker ps` 看端口列。
- **修法**：渲染新端口后**显式重建容器**（让声明与事实对齐），不要只改 compose 文件就 `up`。
- **状态**：已修复。

## D. 卸载与重装

### P13 重装后要手动清一次「服务器地址」
- **症状**：重装/换端口后控制台仍指向旧地址，用户得手动改一次才能登录。
- **根因**：控制台的服务器地址存在浏览器 `localStorage`，按 **origin** 隔离；端口变了就是新 origin，但旧值仍会被读到（或注入脚本只在「无值」时才写，旧值把新值挡住了）。
- **怎么确认**：浏览器 Application → Local Storage 看该键值与当前访问 origin；清掉后是否立刻正常。
- **修法**：注入策略改为「同主机、不同端口 → 覆盖；不同主机 → 不动」，既修掉端口残留，又不会在用户有意指向远端时把它改回去。
- **状态**：已修复。

### P14 卸载后用户以为数据丢了
- **症状**：卸载再装，看不到原来的数据，用户认为被删除。
- **根因**：升级/换库时旧库被**改名保留**为 `data.old-<时间戳>`，并未删除；但目录名变了，界面上看不到。
- **怎么确认**：`ls -ld ${TRIM_PKGVAR}/*` 找 `data.old-*`；看卸载/升级日志里是否记录了改名与路径。
- **修法**：日志中直接给出「搬回」的具体命令；文档（`docs/data-location.md`、`docs/faq.md`）写明该行为与恢复步骤。
- **状态**：已修复（残留目录永远不自动删，这是刻意设计）。

### P15 卸载会清凭据，也会移除应用使用的镜像 tag
- **症状**：卸载后重装，凭据没了，且拉取镜像又变慢/失败。
- **根因**：平台的卸载流程会清理应用凭据，并移除该应用使用的镜像 tag。
- **怎么确认**：`docker images | grep <image>` 卸载前后对比；重装后先看拉取日志。
- **修法**：重装前先 `sudo docker pull <image>:<tag>` 预热；把这条写进 `docs/install-fnos.md` / `docs/upgrade-safety.md` 的卸载重装说明。
- **状态**：仍有边界（平台卸载行为，改不了；只能文档前置告知）。

## E. 打包与 CI

### P16 `fnpack build` 失败时退出码仍是 `0`
- **症状**：CI/脚本一路绿灯跑到底，但没有产物，或产物是旧的。
- **根因**：`fnpack build` 失败时不返回非零退出码，`set -e` 与 `&&` 都拦不住。
- **怎么确认**：看输出的最后几行有没有 `Packing successfully`；`ls -l` 产物时间戳是否更新。
- **修法**：构建步骤**按输出关键字判成败**（必须出现 `Packing successfully`），并额外校验产物存在与大小非零。
- **状态**：仍有边界（工具行为，不可改；靠工作流里的关键字断言兜住）。

### P17 版本号不能写四段；而 `1.04.01` 更危险
- **症状**：写四段版本号时打包被拒；或者更糟——打包**成功**了，但应用中心显示的版本号与预期不同。
- **根因**：`fnpack` 只接受 `x.y.z` 或 `x.y.z-N`。`1.04.01` 这类带前导零的写法能过打包，但会被解析成 `1.4.1`（语义完全相反）。
- **怎么确认**：`grep '^version' manifest`；打包后从 `.fpk` 里读出 `manifest` 再确认一次；`preflight` 里对格式做断言。
- **修法**：`scripts/stamp-manifest.sh` 约束为 `x.y.z` 或 `x.y.z-N`，并在 `preflight` 拒绝前导零与四段号；版本号由 stamp 单一来源生成，不手改 `manifest`。
- **状态**：已修复（流程约束）；仍有边界（工具本身不拦 `1.04.01`，只能靠 preflight）。

### P18 本地一切正常，CI 报脚本不可执行
- **症状**：本地 `preflight` 全绿；CI 上 `cmd/*` 或 `scripts/*` 报 `Permission denied`。
- **根因**：仓库 `core.filemode=false`，脚本以 `100644` 入库；本地文件系统上的 `+x` 不会进 git。**只有干净克隆**才暴露。
- **怎么确认**：`git ls-files -s cmd scripts` 看模式位是 `100644` 还是 `100755`；在一个全新克隆目录里跑一遍。
- **修法**：`core.filemode=true` 并把脚本以 `100755` 提交；CI 里加一条「干净克隆 + 直接执行」的冒烟。
- **状态**：已修复。

### P19 离线版：镜像放错位置会被 `fnpack` 静默丢弃
- **症状**：包打出来了、还显示打包成功，但包里没有镜像；装到设备上离线拉不到。
- **根因**：镜像文件**必须放在 `app/` 下**才会进包；放在 fpk 根目录会被 `fnpack` 静默丢弃（不报错）。另外包内 tar 需可读、`docker load` 必须放 `install_init` —— 因为平台会在 `install_callback` 之前就用模板起容器。
- **怎么确认**：解开产物看 `tar -tzf <fpk>` 里 `app/` 下有没有镜像文件；`app/images` 计数是否为 0（在线包应为 0，离线包应非 0）。
- **修法**：镜像固定落 `app/`；`preflight` 对「包形态 ↔ `app/images` 非空」做一致性断言；`docker load` 放 `install_init`，包内 tar 权限改为可读。
- **状态**：已修复（离线形态已按此设计）；离线 job 当前未启用，启用时按此验证。

## F. 架构

### P20 `install_init` 硬拒非 x86，ARM 设备连安装都进不去
- **症状**：aarch64 设备上安装直接失败，日志里出现「本包仅支持 x86」。
- **根因**：`install_init` 里写过一段只允许 x86 的硬拒逻辑（在线包本身无架构相关二进制，硬拒是历史遗留）。
- **怎么确认**：`grep -n 'x86' cmd/install_init`；`uname -m` 确认设备架构。
- **修法**：改为按**包形态**判断——在线版接受 `amd64`/`arm64`，其它架构 `WARN` 但继续；离线版按包内镜像的实际架构校验（`normalize_arch` / `check_arch`）。
- **状态**：已修复（`v1.0.4-2`，`platform=all`）。**注意：ARM 是「可安装」而非「已真机验证」**，Release 说明里给了 7 条自测，尚无 arm 设备跑过。

## 维护约定

1. 新增条目必须**先复现、再写**；没复现的推测写进 issue，不进本文。
2. 状态只有 `已修复` / `仍有边界` 两种。写「仍有边界」时必须给出**规避手段**，否则说明还没定位清楚。
3. 同一条目修法若依赖平台行为，请在根因里点明「平台行为，不可改」，避免下一个人把它当代码 bug 反复查。
4. 条目编号 P01 起只增不改；条目作废时保留编号并标注「已作废 + 作废原因」，不要删除（删除会让旧链接失效）。

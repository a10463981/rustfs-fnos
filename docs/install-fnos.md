# 在飞牛 fnOS 上安装 RustFS

本文从零开始：下载 → 校验 → 安装 → 首次配置 → 建第一个桶 → 用 S3 客户端连上去 → 升级 → 卸载。

> 前提：本文假设你已经在浏览器里登录了飞牛 fnOS，并且有管理员权限。
> 如果你只是想确认下载的包没被替换过，直接跳到 [docs/verify.md](verify.md)。
> 遇到异常行为，先看 [docs/faq.md](faq.md) 顶部的「用户可见行为总表」。

---

## 一、前置条件

装之前先确认这四件事，能省掉 80% 的「装完起不来」：

| # | 检查 | 怎么确认 | 不满足会怎样 |
|---|---|---|---|
| 1 | **架构是 x86** | 飞牛 fnOS 的「系统信息」里看处理器型号；或 SSH 登录后 `uname -m` 看到 `x86_64` | ARM 设备（`aarch64`）**不支持**，装上也跑不起来 |
| 2 | **Docker 服务在运行** | 应用中心里能看到 Docker 相关入口且状态正常；SSH 里 `docker version` 能看到 Server 段 | 应用装上了但一直启动不了 |
| 3 | **有一个可用的存储空间** | 飞牛「存储空间管理」里至少有一个已挂载的卷 | 没有地方放数据，安装会失败或数据落到系统盘 |
| 4 | **设备能访问镜像仓库** | 见第五节「镜像怎么到位」 | 启动时卡在等镜像，表现为启动失败 |

关于磁盘：对象存储会随着写入持续增长，**不要把它放在系统分区**。建议单独一块盘或单独一个卷。RustFS 的数据目录会落在你安装时选择的存储空间下。

## 二、下载与校验

### 1. 下载

到本仓库的 **Releases** 页面，找到你要装的版本（首次安装就用最新版本），下载两个文件：

- `rustfs-fnos-1.0.4-x86.fpk`（安装包本体）
- `SHA256SUMS`（校验值清单）

> 只有 x86 版本。文件名里的 `1.0.4` 是本包版本，对应上游 RustFS 1.0.4。

### 2. 校验（强烈建议做，30 秒）

在你下载文件的那台电脑上执行（三个系统任选其一）：

**Linux**

```bash
sha256sum -c SHA256SUMS
# 期望看到：rustfs-fnos-1.0.4-x86.fpk: OK
```

**macOS**

```bash
shasum -a 256 -c SHA256SUMS
```

**Windows（PowerShell）**

```powershell
Get-FileHash .\rustfs-fnos-1.0.4-x86.fpk -Algorithm SHA256
# 把输出和你下载的 SHA256SUMS 里那一行对比，必须完全一致
```

**比对失败怎么办**：不要安装。删掉文件重新下载；连续两次不一致就别装了，把情况报到 Issue。详细说明见 [docs/verify.md](verify.md)。

### 3. 把包装到 NAS 上

如果 NAS 能直接下载，你可以跳过这一步。否则把 `.fpk` 传到 NAS 上，三种方式都行：

- 在飞牛「文件管理」里上传到任意共享目录（**最简单**）；
- 用 SMB 从电脑复制过去；
- SSH 上传：`scp rustfs-fnos-1.0.4-x86.fpk admin@<NAS地址>:/tmp/`

## 三、安装

1. 打开飞牛 fnOS → **应用中心**。
2. 左下角点 **「手动安装」**。
3. 选择你刚上传/下载的 `rustfs-fnos-1.0.4-x86.fpk`。
4. 系统会提示这是第三方应用来源，确认继续。
5. 进入安装向导，按下一节的字段说明填写。
6. 点安装，等待完成。首次安装需要把镜像放到设备上，**可能等几分钟**，取决于你的网络（见第五节）。

> 也可以命令行安装（有 SSH 权限时）：`appcenter-cli install-fpk /path/to/rustfs-fnos-1.0.4-x86.fpk`。
> 但注意：**这个命令只适合首次安装**，对已安装的应用会直接返回「已安装」，不会升级（见第六节）。
> 图形界面的手动安装是普通用户的真实路径，第一次装建议走界面。

---

> ## 📍 数据放哪里，请在这一步决定（安装向导里最重要的一项）
>
> 向导的第一个字段就是**数据存放位置**。它不是一个可以随手点「下一步」的选项：
>
> - **默认位置是应用自己的数据目录**。它跟着应用走，通常落在系统所在的那个卷上——而那个卷往往不大，对象存储又只会越长越大。
> - **强烈建议改成你自己选的大容量存储空间**（放影视库、放备份的尤其如此）。系统卷被塞满，会让整台 NAS 出问题。
> - **更要紧的是安全边界**：放在应用默认目录里的数据，会被应用的卸载动作、以及安装失败后的平台回滚**一并清理**（后者我们在真机上验证过）；放到你自己的存储空间里，就不在这次清理范围内。
> - 其实**两个时机都能设**：安装向导里直接填；装好之后也可以在 应用中心 → 该应用 → **配置/设置** 里改（该字段在配置向导里的可用性以你设备上的实际界面为准）。
> - **改路径不会自动搬数据**。换目录之后旧数据还在原地，需要你自己迁移。
>
> 迁移示例（把两个路径换成你的实际值；先停止应用再操作）：
>
> ```bash
> # 1) 应用中心点「停止」
> # 2) 复制到新位置（不是 mv，先保住原地那份）
> sudo cp -a /vol1/@appdata/rustfs-fnos/data/. /vol2/rustfs-data/
> # 3) 修正归属（容器内以 UID/GID 10001 运行）
> sudo chown -R 10001:10001 /vol2/rustfs-data
> # 4) 在「配置/设置」里把数据目录改成 /vol2/rustfs-data，保存后启动
> # 5) 控制台里确认桶与文件都在，再删旧目录
> ```

## 四、向导字段说明

| 字段 | 含义 | 默认值 | 怎么选 |
|---|---|---|---|
| **数据存放位置** | RustFS 的数据（桶与对象）落在哪里 | 由安装流程选择存储空间 | 选**容量够、非系统盘**的存储空间。单盘部署**以后不能原地扩容**（上游限制），一次选够 |
| **S3 API 端口** | 其它应用 / S3 客户端连接的**宿主侧**端口 | `9200` | 保持默认即可。被占用就换一个空闲端口（如 9300） |
| **控制台端口** | 浏览器打开管理界面的**宿主侧**端口 | `9201` | 保持默认即可。被占用就换（如 9301） |
| **管理员账号** | 登录 RustFS 控制台，同时也是给其它应用用的 S3 Access Key | **必填**（没有默认值） | 自己设一个好记但不好猜的，例如 `rustfs-admin`；**不要**用 `admin`、`root`、`rustfsadmin` |
| **管理员密码** | 上面那个账号的密码（S3 Secret Key） | **必填**（没有默认值） | **你自己定、也由你自己记**，建议存进密码管理器。忘了可以在「配置/设置」里重设 |

> **端口只在宿主侧生效。** 容器内部一直监听它自己的固定端口（9000 / 9001），你改的是「NAS 的哪个端口映射到它」。所以改端口不需要改任何应用配置，也不影响已经建好的桶。
>
> 关于凭据：**账号和密码由你在向导里当场填**，不需要事后去任何文件里找。本包不会套用上游文档里那组公开的默认账号 `rustfsadmin` / `rustfsadmin`——那是公开的，谁都知道。

安装完成后：桌面出现「RustFS」图标；应用中心里能看到它的运行状态；可以启动/停止。

## 五、镜像怎么到位（这条最容易卡住）

**应用自己不能联网拉镜像。** 它以一个专用低权限用户（包用户）运行，而 fnOS 镜像加速站要求请求带一组签名头，那组头只写在 **root 的** docker 配置里。所以应用运行期去拉镜像一定超时——**这是平台设计，不是故障**。

镜像由**应用中心（root）**或**你自己用 `sudo`** 拉下来。正常流程是这样：

1. 安装/升级时，应用发现「配置里声明的镜像」和「容器实际在跑的镜像」不一致；
2. 如果目标镜像已在本地 → 应用自己重建容器并校验；
3. 如果还不在本地 → 应用登记一个「待校验」状态，等镜像到位（宽限 15 分钟）；
4. 你手动把镜像拉到本地，然后回应用中心「停止 → 启动」，应用发现镜像就位，完成切换。

**手动拉镜像：**

```bash
# 以管理员身份（root 的 docker 配置才带镜像站签名头）
sudo docker pull rustfs/rustfs:1.0.4
```

- 成功：回应用中心「停止 → 启动」。
- 失败且是超时：设备出口网络问题，先解决网络（或配镜像加速）。
- 失败且提示 `no such manifest` / `not found`：tag 打错了，或者上游没发这个 tag。核对 Release 说明里写的镜像 tag。
- 完全没外网：在别处 `docker save` → 传到 NAS → `docker load`。

## 六、升级指引

### 正确路径：应用中心 Web UI

| 方式 | 结果 |
|---|---|
| 应用中心 → 上传新包 / 升级入口 | ✅ **正确**。会走升级流程：记录当前镜像、备份配置、按新包重建容器 |
| `appcenter-cli install-fpk <新包>` | ⚠️ 对已安装应用返回「已安装」，**不会升级** |
| `appcenter-cli install-local` | ❌ **等于卸载再安装**：凭据被重新生成，所有 S3 客户端要改配置 |
| 手工改 compose + `docker compose up` | ❌ 绕过校验流程，状态会与实际不一致 |

### 升级时会发生什么

1. **服务会中断一会儿。** 容器要重建，这期间 S3 API（9200）与控制台（9201）都不可用，通常几秒到几十秒。**建议在没人用的时候做**，正在跑的备份任务会被中断。
2. **数据不会丢。** 桶与对象在数据目录里，不在容器里，重建容器不影响。
3. **镜像可能不会立刻换好。** 如果新镜像还没在设备上，应用会进入「待校验」状态（最多等 15 分钟）。这期间状态可能显示为运行中，也可能在超时后变成失败。

### 升级后怎么确认真的升了

```bash
# 看容器实际在跑哪个镜像
sudo docker inspect <容器名> --format '{{.Config.Image}}'
```

再对比 Release 说明里写的镜像 tag。两者一致才算升级完成。

### 回滚

- 应用能做的回滚是：**把镜像引用改回上一版，再重建容器**。
- **回滚不还原**端口、环境变量、数据目录路径这些配置。如果新包除了镜像之外还改了这些，回滚后是「旧镜像 + 新配置」的混合体，需要人工核对。
- 回滚依赖两样东西：应用记录下来的上一版镜像引用，以及那个镜像还在本地。如果这次是「启动时发现漂移」而非正常升级流程，应用可能没有记录，日志里会直接给出该改回的 ref，或者让你用 `sudo docker images` 自己找。
- 状态变失败时，应用的日志里会写「三步修复 + 回滚命令」，照着做即可。

## 七、安装/升级失败时可能发生什么

### 两种失败阶段，后果完全不同

| 失败发生的阶段 | 典型例子 | 对数据的影响 |
|---|---|---|
| **向导校验阶段**（安装任务还没创建） | 必填字段没填、端口格式不对、必选项没选 | 应用不会被创建；**已有数据不受影响**（有对照实验：这一阶段的失败之后，数据目录与凭据都还在） |
| **应用初始化阶段**（安装任务内，`install_init` 报错） | 初始化脚本异常、目录创建失败、端口被占导致脚本失败 | 平台会执行**失败回滚**（日志里记作 `rollback`），把 `/vol1/@appdata/<app名>` 与 `/vol1/@appconf/<app名>` **整个删除** —— 已有数据与凭据一起消失（真机复现） |

- 「装失败」不等于「什么都没变」。第二种情况下，失败**会连带删掉数据与凭据**。
- **尚未确认**：在应用中心用新包做「升级」时若失败，是否同样触发回滚、是否也删数据。我们没有实测证据，因此**请按最坏情况准备：升级前先备份**（做法见 [README「升级前必做」](../README.md)）。

### ⛔ 不要用 `appcenter-cli install-local` 装这个包

命令行里唯一会被旧文档提到、但**不该用**的命令就是它：

```bash
# ❌ 不要这样装
appcenter-cli install-local -d /path/to/rustfs-fnos/deploy/fnos
```

两个理由，都实测过：

1. **会报 `10237`**：`code 10237: fork/exec /tmp/appcenter.pack.<reqid>/cmd/install_init: permission denied`。原因是它把**源码目录**原样复制到临时目录再执行，而源码目录通常是 `700`，包用户既进不去目录也执行不了脚本。从 `.fpk` 安装时平台会把 `cmd/*` 规范化成 `755`，所以不会踩这个坑。
2. **它的语义是「卸载再安装」**：凭据会被重新生成，所有已接入的 S3 客户端都要改配置（见第十二节关于卸载的说明）。

正确做法：**应用中心 → 手动安装 → 上传 `.fpk`**。

### 装失败了怎么办（三步）

**第一步：看应用中心给的错误**

应用中心界面上的提示通常只有一句话。要看原文，SSH 登录后查应用中心自己的日志：

```bash
sudo grep -i rustfs-fnos /var/log/trim_app_center/error.log | tail -20
sudo grep -i rustfs-fnos /var/log/trim_app_center/info.log  | tail -20
```

重点看两类行：

- `msg="install error"` —— 失败原因（例如 `10237 … permission denied`）
- `msg=rollback` —— **这一行一旦出现，立刻去检查数据还在不在**

**第二步：看本应用自己的日志**

```bash
sudo tail -50 /var/log/apps/rustfs-fnos.log 2>/dev/null
```

这里的文字是给用户看的「可见错误」，通常直接说明哪一步没通过。

**第三步：确认数据还在不在**

```bash
# 数据目录（桶与对象）
ls -ld /vol1/@appdata/rustfs-fnos/data 2>/dev/null && sudo du -sh /vol1/@appdata/rustfs-fnos/data
# 配置与凭据
ls -ld /vol1/@appconf/rustfs-fnos 2>/dev/null
# 你之前做的备份
ls -d /vol1/@appdata/rustfs-fnos/data.bak-* 2>/dev/null
```

- **目录还在、大小正常** → 数据没问题，按日志里的原因修配置后重试。
- **目录不存在、但有 `data.bak-*`** → 用备份恢复（命令见 [README「升级前必做」](../README.md)），恢复后再启动应用。
- **目录不存在、也没有备份** → 数据已经没了，这一步没有别的补救手段。这也是为什么升级前那句备份命令值得花 30 秒。

> 提醒：如果 `/vol1` 不是你的第一个存储空间，把路径里的 `/vol1` 换成实际卷（`ls -d /vol*/@appdata/*/data` 可以看）。应用名 `rustfs-fnos` 也换成你实际的 appname。

## 八、端口冲突怎么办

现象：安装向导提示端口被占用，或装完启动失败、日志里出现「address already in use」。

1. 先看 9200/9201 是不是被别的应用占了。SSH 里执行：

   ```bash
   sudo ss -lntp | grep -E ':(9200|9201)\b'
   ```

2. 有输出就说明被占了，看最后一列是谁的进程。
3. 回应用中心 → 该应用 → 配置/设置，把**宿主侧端口**改成一个空闲的（例如 9300 / 9301），保存后重启应用。
4. 改完记得告诉用 S3 的应用新端口。容器内部端口没变，所以不需要动应用自己的配置。

> 常见撞车对象：MinIO 及同类工具习惯用 9000/9001；本包特意用 9200/9201 就是为了避开它们。如果你自己也跑了 MinIO 之类的服务，确认它的端口后再定。

## 九、打开控制台、创建第一个桶

1. 点桌面图标；或浏览器直接访问 `http://<NAS地址>:9201`。
2. 用向导里设的 Access Key / Secret Key 登录。
3. 左侧找 **Buckets / 桶** → 新建。
4. 名字用小写字母、数字和连字符（例如 `backup`、`photos-2026`）。**桶名建好后一般不建议改**，因为引用它的应用都要跟着改。
5. 进去后点上传，随便传一个文件测试。传完能列出来、能下载，就说明存储链路通了。

健康检查（不用登录，确认服务活着）：

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://<NAS地址>:9200/health/ready
# 200 = 就绪
```

## 十、用 S3 客户端连 9200（最小示例）

关键参数只有三个：

| 参数 | 值 |
|---|---|
| Endpoint | `http://<NAS地址>:9200` |
| Access Key / Secret Key | 向导里设的那组 |
| Region | 随便填（不校验，例如 `us-east-1`），部分客户端必填 |

**aws-cli 示例**

```bash
export AWS_ACCESS_KEY_ID='你的 Access Key'
export AWS_SECRET_ACCESS_KEY='你的 Secret Key'

# 列桶
aws --endpoint-url http://192.168.1.10:9200 s3 ls

# 传一个文件
aws --endpoint-url http://192.168.1.10:9200 s3 cp ./test.txt s3://backup/test.txt

# 看桶里有什么
aws --endpoint-url http://192.168.1.10:9200 s3 ls s3://backup/
```

**curl 示例（不依赖任何客户端）**

```bash
curl -i http://192.168.1.10:9200/
```

能返回 HTTP 响应（哪怕是 `403 AccessDenied`）就说明端口通、服务活着；返回 `Connection refused` 才是没起来。

**其它应用怎么填**

支持 S3 的软件一般都有「自定义端点 / Self-hosted S3」选项，填：

- Endpoint：`http://<NAS地址>:9200`
- Path-style 访问：如果软件有这个选项，**打开**（不少客户端默认用虚拟主机风格，会在 NAS 环境下解析失败）
- 不需要 TLS / 关闭 HTTPS
- Bucket 先在本应用控制台建好，再在对方应用里填名字

## 十一、忘记凭据怎么办

**先试最省事的一条：** 应用中心 → 该应用 → **配置/设置**，在向导里把账号密码重设一遍。不用卸载，数据也不动。

sudo ls -l /var/apps/rustfs-fnos/etc/
# 找到保存凭据的配置文件后查看（文件名以实际为准）

## 十二、卸载与数据（**注意：会清凭据**）

在应用中心里卸载时，会问你**数据**怎么处理：

| 选择 | 结果 | 什么时候选 |
|---|---|---|
| **保留数据** | 桶与对象**还在**，以后重装能继续用 | 只是重装/暂时不用了 |
| **删除数据** | 数据目录被清空，**不可恢复** | 确定不再需要里面的东西，且已经另外备份 |

**默认请选保留。** 删数据的操作没有二次确认的价值——它删掉的东西通常没有第二份。

### 但「保留数据」不等于「什么都没变」

不管数据怎么选，**卸载都会清掉应用的配置目录，包括访问凭据（Access Key / Secret Key）**。重装时你要**重新填一组**（向导里填），旧的那组立即失效：

- 已经接入的备份工具、媒体服务器、其它自建应用，下一次访问会收到 `403 InvalidAccessKeyId`；
- 它们不会自动更新，也不会有人提醒你，通常是「某天后备份开始失败」才被发现。

所以卸载/重装前，请先想清楚这件事，并准备好逐个更新这些客户端。建议顺序：

1. 先把接入方清单列出来（哪些机器/应用在用这组凭据）；
2. 卸载 → 重装 → 记下新的 AK/SK；
3. 逐个更新接入方，改完一个测一个（用 `aws s3 ls` 之类的最小命令验证）；
4. 全部改完再回来看备份任务是否恢复正常。

### 还有一件事：卸载会移除镜像 tag（实测）

卸载之后，`docker images` 里 `rustfs/rustfs:<版本>` 这个 **tag 会消失**（镜像本体如果还被 `:latest` 之类别的 tag 引用着就还在，只是没有那个版本号的名字了）。

后果：重装同一个版本时，平台在本地找不到这个 tag 就会去拉；而**应用自己拉不动镜像**（运行身份是低权限用户，镜像站的签名头只写在 root 的 docker 配置里）。表现出来是：

- 装完了但打不开控制台；
- 或者等约 15 分钟后状态被判失败，日志里写「拉取失败 / 升级未生效」。

处理只要两行：

```bash
# 1) 先把对应版本的镜像拉回本地（版本号以你要重装的包为准）
sudo docker pull rustfs/rustfs:1.0.4
# 2) 回应用中心「停止 → 启动」，然后确认控制台能开
curl -s -o /dev/null -w '%{http_code}\n' http://<NAS地址>:9201/rustfs/console/    # 200 = 起来了
```

顺带一句：这也是**卸载前最好先记下自己装的是哪个版本**的原因——重装要靠它把镜像找回来。`appcenter-cli list` 里能看到，或者看当初下载的那个包名。

卸载后建议顺手确认端口是否释放：

```bash
sudo ss -lntp | grep -E ':(9200|9201)\b'
```

有残留说明有进程没退出，重启一下设备或手工处理。

## 十三、常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 装完桌面有图标，但打开是空白/报错 | 容器没起来，或镜像还没到位 | 应用中心看状态；`sudo docker images` 看目标 tag 在不在；不在就 `sudo docker pull` 后「停止→启动」 |
| 日志里「拉取失败 / 超时」 | **应用自己不能拉镜像**（平台设计） | 见第五节：`sudo docker pull` 后「停止→启动」 |
| 升级后状态变成失败，日志说「升级未生效」 | 容器还在跑旧镜像，宽限期（15 分钟）已过 | 拉好目标镜像 → 「停止→启动」，应用会自己重建并校验；日志里有三步修复与回滚命令 |
| 启动失败，日志里有 `permission denied` | 数据目录归属不对（容器以非 root 用户运行，需要该用户可写） | 见下一条命令；或重新安装并让安装流程处理目录权限 |
| 一直卡在「启动中」 | 正在等镜像（几百 MB），或网络不通 | 等；或按第五节手动 `sudo docker pull` |
| 控制台能开，S3 客户端连不上 | 端口填错 / 对方应用用了 HTTPS / 虚拟主机风格寻址 | 确认 `http://<NAS>:9200`、关掉 HTTPS、开启 path-style |
| 用上游默认账号 `rustfsadmin` 登不进去 | 本包不套用上游默认账号，凭据是你在安装时填的那组 | 用向导里填的账号密码；忘了就「配置/设置」重设 |
| 重装/升级后客户端报 `403 InvalidAccessKeyId` | 卸载重装换了凭据（升级本身不会换） | 用新凭据更新客户端；确认自己用的是升级入口而不是 `install-local` |
| 空间很快满了 | 对象存储持续增长，且可能有多版本/未清理的旧对象 | 在控制台里检查桶用量；确认存储空间容量；必要时迁移 |

修正数据目录归属（**仅在确认是权限问题时使用**，把 `<数据目录>` 换成实际路径）：

```bash
# RustFS 容器以 UID/GID 10001 运行，宿主目录必须可被该用户写入
sudo chown -R 10001:10001 <数据目录>
```

# 升级/重装前的数据安全（必读）

本文只讲一件事：**在你动手升级或重装之前，怎么用 30 秒把数据兜住。**

---

## 为什么需要这一步

我们的应用把对象数据放在应用自己的数据目录里（`/var/apps/rustfs-fnos/var/data`，物理位置是 `/vol<N>/@appdata/rustfs-fnos/data`）。

真机实测发现一条**不受我们控制的清空路径**：

> appcenter 在安装/升级任务**内部**失败时，会执行一次 `rollback`（日志里是 `msg=rollback`）。
> 在我们观测到的那次事故里，rollback 之后 `@appdata/<app>`（数据）与 `@appconf/<app>`（配置与凭据）**双双消失**。

对照实验让这条结论更清楚：

| 失败发生的阶段 | 数据结果 |
|---|---|
| 失败在**安装任务创建之前**（例如向导字段校验被拒） | 数据**完好** |
| 失败在**安装任务内部**（例如生命周期脚本抛错） | 触发 `rollback`，**数据消失** |

也就是说：**「升级/安装失败」有可能连带删掉数据目录，而这不是我们的脚本干的**（我们的卸载脚本在「保留数据」分支里没有任何删除动作，日志也只打印不删）。

我们无法改变 appcenter 的 rollback 行为，所以只能在你动手之前先把数据复制一份。

---

## 什么时候做

**在做下面任何一件事之前：**

- 在应用中心上传新版本 `.fpk` 升级；
- 卸载后重装；
- 用 `appcenter-cli` 装包（除首次安装外，都不建议）；
- 任何会改变 `image:` 或让应用重建容器的操作。

首次安装不需要（那时还没有数据）。

---

## 怎么做

### 一条命令

```bash
sudo bash scripts/backup-data.sh
```

它会：

1. 把 `/var/apps/rustfs-fnos/var/data` 整份 `cp -a` 到 **`/vol<N>/rustfs-fnos-backups/data.bak-<时间戳>/`**；
2. 打印体积、条目数，并校验「条目数一致」；
3. **只复制，不移动、不删除原数据**；
4. 空间不足时**提前失败**（不会写出半份备份）；
5. 目标已存在时**绝不覆盖**（自动加序号）。

常用参数：

```bash
# 指定备份根目录（必须不在 @app* 里面）
sudo bash scripts/backup-data.sh --dest /vol2/rustfs-backups

# 备份完只保留最近 3 份
sudo bash scripts/backup-data.sh --prune 3

# 只看计划，不动磁盘
sudo bash scripts/backup-data.sh --dry-run
```

### 为什么要以 root 运行

备份要保留属主与权限（`cp -a`）。容器以非 root 用户（UID/GID `10001`）运行，它写出来的文件属主不是你。以 root 复制才能保证「放回去之后权限是对的」。

脚本没有 root 时会直接拒绝（除非你显式加 `--allow-nonroot`，那只用于本地冒烟）。

---

## 备份放在哪，为什么不能放在应用目录里

**默认落点：`/vol<N>/rustfs-fnos-backups/`** —— 卷根下的一个普通目录，与 `@appdata`／`@appconf` 同级，但**不在它们里面**。

理由（这条很重要）：

| 候选落点 | 能不能用 | 原因 |
|---|---|---|
| `/vol<N>/@appdata/<app>/…` | ❌ **绝对不行** | rollback 会连它一起删，备份等于白做 |
| `/vol<N>/@appconf/<app>/…` | ❌ | 同上（事故里 `@appconf` 也一起消失了） |
| `/vol<N>/@apptemp/<app>/…`（`TRIM_PKGTMP`） | ❌ | 语义就是临时，重启/清理可能被清 |
| `/vol<N>/@apphome/<app>/…`（`TRIM_PKGHOME`） | ❌ | 同属 `@app*`，无法保证不参与回滚（**需核实**） |
| 共享目录（`data-share`） | ⚠️ 不推荐 | 本应用没有声明 `data-share`（刻意不给用户直接看内部数据）；而且备份会出现在文件管理器里，误删风险高 |
| **`/vol<N>/` 下的普通目录** | ✅ **推荐** | 不在 `@app*` 内，不参与回滚；用户平时看不到，也不容易手滑删掉 |

脚本内置了护栏：只要 `--dest` 落在 `@appdata` / `@apptemp` / `@appconf` / `@apphome` / `@appmeta` / `@appcenter` 之内，**直接拒绝执行并说明原因**。

---

## 备份占多少空间

约等于数据目录当前体积（`cp -a` 全量复制，不做增量）。

- 数据 10 GB → 备份 10 GB → 那一下需要 **20 GB 可用**（原数据 + 备份）。
- 脚本会先算「源体积 + 10% + 10 MB」再跟可用空间比，不够就提前失败。
- `--prune 3` 可以把历史备份控制在 3 份；记得按你的数据量 × 份数 预留空间。

如果空间确实不够，两条替代路径：

1. **存储空间快照**（如果文件系统支持）：比复制快、几乎不占额外空间，但快照与源数据同盘，属于「防误删」级别，不防盘坏。
2. **只备份配置**：`/vol<N>/@appconf/rustfs-fnos/`（几 KB）——但注意这条**救不了数据**，只救凭据与设置。

## 真出事了怎么回退

**前提：先停应用，别卸载。** 卸载会再触发一次目录清理。

```bash
# 1) 应用中心里把「RustFS（非官方）」停止

# 2) 把当前数据挪开（不要直接删，留个后路）
sudo mv /var/apps/rustfs-fnos/var/data \
        /var/apps/rustfs-fnos/var/data.broken-$(date +%Y%m%d-%H%M%S)

# 3) 把备份放回去（注意：备份目录名换成你自己的那份）
sudo cp -a /vol1/rustfs-fnos-backups/data.bak-20261027-182404 \
           /var/apps/rustfs-fnos/var/data

# 4) 应用中心里「启动」，然后验证
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9200/health/ready   # 期望 200
```

验证点：控制台能打开、桶与对象都在、`main status` 返回 0。

第 2 步挪开的那份 `data.broken-*` 在确认无误后再自行清理——**回退这一步不要省，直接覆盖原数据就没有第二次机会了**。

## 为什么应用不自己在升级时自动备份

考虑过，结论是**不做**，原因有三条，都是硬约束：

1. **权限**：生命周期脚本以**包用户**运行（真机实测 uid 非 root）。而 `/vol<N>/` 根目录属于 `root:root 755`，包用户**写不进去**。要写到安全位置，就得把应用改成 `run-as: root` —— 这违背我们刻意保持的最小权限。
2. **位置悖论**：包用户唯一能写的是自己的 `var` / `etc` / `tmp`，而这几个目录**恰好都在 rollback 的删除范围内**。也就是说「自动备份能写的地方 = 会被删的地方」，自动备份等于白做。
3. **阻断策略没法定**：如果备份失败就阻断升级，那么空间不足、权限异常时用户会**连升级都做不了**；如果不阻断，用户会以为「有自动备份」，反而更放松。

所以采取的是「**显式的手工一步 + 文档写清**」：由管理员在升级前跑一条命令，出问题时有明确的回退路径。

> 如果你希望它更省事，可行的替代是：**用 fnOS 的存储空间快照**（如果有），在升级前手动打一个快照——同样在 `@app*` 之外，且比复制快。

---

## 这份备份不防什么

| 不防 | 说明 |
|---|---|
| 磁盘损坏 / 阵列故障 | 备份与源数据在同一块盘上。要防硬件故障，请做快照 + 异地复制（`rsync` 到另一台机器） |
| 误删对象 | 这是对象存储层面的问题，靠版本控制（versioning）或桶复制，不是本文的范围 |
| 上游改了数据格式 | 跨大版本升级前的格式兼容性请先看上游 Release Notes；本文只保证「升级失败能退回去」 |

---

## 一句话小结

> **升级前跑一次 `sudo bash scripts/backup-data.sh`，确认它打印了「条目数（与源一致）」。**
> 备份落在 `/vol<N>/rustfs-fnos-backups/`，不在 `@app*` 里，所以 rollback 删不到它。

## 切到自定义目录后，原来的数据去哪了（重要）

第一次把数据目录从「默认位置」改到「自定义目录」时，原来的默认库**会被改名保留**，不是删除：

```
/vol1/@appdata/rustfs-fnos/data          ← 应用现在用的（新建的空库）
/vol1/@appdata/rustfs-fnos/data.old-20261027193301   ← 你原来的库，完整保留
```

为什么必须改名：同一个路径不可能**既**是真实目录、**又**是指向别处的符号链接。所以只能「把旧的挪开、让链接占位」，代码选择的是**改名保留**（不是删除）。

**代价**：如果之后又「恢复默认位置」，应用面对的是那个**新建的空库**，于是你会觉得「数据不见了」——其实它在 `data.old-*` 里。

### 应用会主动告诉你

从 v11 起，执行「恢复默认位置」时，日志里会列出所有 `data.old-*` 的**完整路径、体积、条目数**，并给出可直接粘的两条命令：

```
[rustfs-fnos] 旧数据目录（完整保留，未删除）：/vol1/@appdata/rustfs-fnos/data.old-20261027193301　体积 21K，条目 2
[rustfs-fnos] 说明：这些是你之前「切到自定义目录」时，原来的默认数据被整体改名保留在这里（一个字节都没删）。
[rustfs-fnos]       要搬回来：先在应用中心「停止」应用，再复制粘贴执行下面几条——
[rustfs-fnos]   sudo cp -a "/vol1/@appdata/rustfs-fnos/data.old-20261027193301/." "/vol1/@appdata/rustfs-fnos/data/"
[rustfs-fnos]   sudo chown -R 996:901 "/vol1/@appdata/rustfs-fnos/data"
[rustfs-fnos]       （源写成「旧目录/.」表示把里面的内容复制进目标目录，不会多套一层子目录；同名文件以旧库为准覆盖）
[rustfs-fnos]       搬完在应用中心「停止 → 启动」；确认数据都在后，可以自行删除 /vol1/@appdata/rustfs-fnos/data.old-* 目录。
```

命令里的路径与 UID:GID 都是**你这台机器的真实值**（上面以 `996:901` 为例），不需要自己替换；体积与条目数同样以你的实际输出为准。

> 与 [docs/data-location.md](data-location.md) 第三节的关系：那边讲**机制与完整的手工步骤**，这边只讲**升级/重装前你会看到什么**。两处说法以真机实测为准（`def-check` 读 404、旧库 21,379 字节仍在），不会互相矛盾。

### 自己动手搬回来

完整步骤（含「先停应用」「`/.` 不能省」「用 `cp -a` 不要 `mv`」「确认后再删」）在
**[docs/data-location.md 第三节「改数据目录会发生什么」](data-location.md)**，这里不重复，免得两份命令各自漂移。

一句话版：

```bash
# 应用中心「停止」→ 复制 → 改属主 → 「启动」
sudo cp -a /vol1/@appdata/rustfs-fnos/data.old-20261027193301/. /vol1/@appdata/rustfs-fnos/data/
sudo chown -R 996:901 /vol1/@appdata/rustfs-fnos/data
```

> 反过来也一样：切到自定义目录后，如果想把数据搬过去，用日志里给的那条 `cp -a`（源是默认目录），而不是指望系统自动搬——我们刻意不做自动搬迁，因为几十 GB 的复制可能几十分钟，中途失败更难收拾。

## 卸载重装：镜像 tag 可能不在了

真机实测：**卸载应用后，`docker images` 里本应用使用的那个 tag（例如 `rustfs/rustfs:1.0.4`）会消失**，只剩 `latest`（同一个 image id）。这是平台在卸载时清理「应用引用的镜像 tag」，不是我们删的。

**影响**：重装时如果本地没有这个 tag，应用不能自己拉（包用户没有镜像站签名头），会进入「待校验升级」状态，15 分钟后才判失败。

**怎么办**（重装前执行一次，10 秒）：

```bash
# 看本地还有没有这个 tag
sudo docker images | grep rustfs
# 没有就拉回来
sudo docker pull docker.io/rustfs/rustfs:1.0.4
```

> 我们**不**在卸载时偷偷 `docker tag` 复制一份保底 —— 那会留下一个没人清理的「僵尸镜像引用」，占着几百 MB。宁可写清这一步。
